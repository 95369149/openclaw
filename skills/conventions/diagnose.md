# 诊断回路

## 规则

**遇到 bug / 异常 / 报错，必须走完整诊断回路，禁止跳步直接猜修法。**

## 诊断六步

```
1. 复现
   ↓
2. 缩小范围
   ↓
3. 提出假设
   ↓
4. 验证假设
   ↓
5. 修复
   ↓
6. 回归验证
```

### 1. 复现

- 能稳定复现才能开始排查
- 记录：触发条件 / 环境 / 输入 / 实际输出 / 期望输出
- 不能复现 → 先找复现路径，不要猜

### 2. 缩小范围

- 二分法定位：哪一层出了问题？
- 候选层：输入 / 解析 / 业务逻辑 / 外部依赖 / 配置 / 环境
- 每次缩小范围后记录排除了什么

### 3. 提出假设

- 基于缩小后的范围，提出 1-3 个最可能的原因
- 每个假设必须是可验证的
- 禁止"感觉是 X 的问题"这类无法验证的假设

### 4. 验证假设

- 最小化验证：改最少的东西来验证假设
- 一次只验证一个假设
- 记录验证结果：成立 / 不成立 / 部分成立

### 5. 修复

- 只修复已验证的根因
- 不顺手修其他"看起来有问题"的地方（scope-lock）
- 修复后说明：改了什么 / 为什么这样改

### 6. 回归验证

- 确认原问题已解决
- 确认没有引入新问题
- 至少运行一次最小验证闭环

## 禁止行为

- ❌ 看到报错直接猜修法，跳过复现和缩小范围
- ❌ 同时验证多个假设
- ❌ 修复后不做回归验证
- ❌ 把"跑通了一次"当成"修好了"

## 交付格式

```
诊断报告：
- 复现路径：[描述]
- 根因定位：[哪一层 / 哪个假设验证成立]
- 修复内容：[改了什么]
- 回归结果：[验证方式 + 结果]
```

## 棘轮价值

防止：

- 同一个 bug 反复出现
- 修了表象没修根因
- 修一个坏一个
