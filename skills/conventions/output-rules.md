# 输出质量标准

## 1. 禁止 slop

输出中禁止以下内容：

- 废话
- 套话
- 空泛总结
- LLM 常见前缀（如“当然可以”“以下是”“希望这能帮助你”一类无信息增益表达）

标准：

- 句子必须带信息，不拿语气填充内容。
- 能删的开场白就删。
- 能直接给结论，就不要绕路。

## 2. 禁止猜测 URL 或路径

URL、文件路径、命令目标、页面位置，必须从实际数据构建，不能凭模式脑补。

要求：

- 仅使用用户提供、工具返回、文件实际存在的数据。
- 缺少关键字段时，明确标注缺失，而不是补全猜测值。
- 引用路径前，优先做最小验证。

## 3. 保留原始措辞，不美化、不改写

对用户原话、会议结论、网页内容、帖子内容，优先保留原始措辞。

要求：

- 不擅自润色成立场更强、更弱或更体面的版本。
- 不把模糊表达写成确定结论。
- 摘录时允许压缩长度，但不允许改变含义。

## 4. 标题简短可扫描

标题应简短、明确、可快速扫描，长度控制在 60 个字符以内。

要求：

- 优先使用具体对象 + 动作。
- 避免“关于……的一些思考”这类低信息密度标题。
- 一个标题只承载一个主任务或主判断。

## 5. 短段落、具体事实、内联引用

默认使用短段落组织内容，每段只承载一个重点。

要求：

- 多写具体事实，少写抽象评价。
- 关键结论紧跟证据或来源。
- 可引用时，优先使用内联引用，而不是把来源悬空放到文末。

## 6. 复杂问题先画 ASCII 结构图

遇到架构、流程、路由、数据流、多步骤任务，优先先画一个 ASCII 图，再给文字解释。

适用场景：

- 多 agent 协作
- skill 路由与触发
- memory / hermes-bridge / gbrain 数据流
- 文档 → PPT / X 抓取 / skillify 等工作流
- 任意“说得清不如画得清”的问题

要求：

- 图先于解释。
- 图中必须体现顺序、依赖、分支或责任边界。
- 若图和后文结论不一致，以图暴露的问题为准，先修正再回答。

## 7. 反证优先，防静默替换

对高风险回答，不能只给结论，要同时给出最可能的失效边界或反证点。

要求：

- 结论后补一句：`可能错在… / 仍需验证… / 当前证据不足于…`。
- 若用户问题被模型悄悄换题，必须明确指出，不得顺着替换后的问题继续写。
- 不确定性默认视为未完成，而不是“差不多完成”。

## 8. 输出前自检

提交前确认：

- 有没有废话或套话可删？
- 有没有任何 URL、路径、名称是我猜出来的？
- 原话是否被我改写走样？
- 标题是否足够短且一眼能扫懂？
- 每段是否具体，并带必要引用？
- 复杂问题是否应该先画 ASCII 图？
- 有没有发生静默替换却没指出来？
