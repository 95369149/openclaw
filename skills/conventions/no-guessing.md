# 不确定先问，能查先查

## 规则

**不确定时，先查；查不到，再问一个关键问题；禁止脑补。**

## 优先级链

```
能查文件/代码/工具 → 查
查不到 → 问 1 个关键问题
明显会跑偏 → 停下来确认
其他情况 → 选最保守方案，继续
```

## 强制检查项

动手前先问：

1. 这个不确定点，能通过读文件/搜索/运行命令解决吗？
2. 如果继续执行，最坏情况是什么？
3. 有没有更保守的方案可以先走？

## 禁止行为

- ❌ 脑补 API 契约、数据结构、配置字段
- ❌ 脑补文件路径、函数名、模块位置
- ❌ 脑补用户意图，然后按脑补结果执行
- ❌ 为了让文档"看起来完整"而编造事实
- ❌ 查不到来源就写成确定结论

## 外部事实特别规定

涉及行业数据、客户信息、竞品参数、外链内容时：

- 查不到 → 写 `TODO: 待补来源`
- 不确定 → 写 `[推断，待验证]`
- 禁止为了完整性编造

## 验证方式

交付时能说清：

- 哪些事实有来源
- 哪些是推断（已标注）
- 哪些是 TODO（已标注）
- 有没有任何脑补内容混入

## 棘轮价值

这条规矩防止的是：

- 事实错误在系统里悄悄传播
- 脑补的路径/字段/数据被后续 agent 当真
- 一个猜测引发一串错误
