# 提示词工程研究笔记 — 2026.02.21

## 一、业界泄露提示词对标分析

### 数据来源
- GitHub: x1xhlol/system-prompts-and-models-of-ai-tools (115k+ stars)
- 2025年4月泄露，覆盖 Cursor / Devin / Manus / Lovable / Replit / v0 / Windsurf 等

### 1. Cursor Agent (57行核心 + 工具定义)

**架构特点：**
- 极度工具导向：system prompt 的 80% 是工具定义（codebase_search / grep / read_file / edit_file / run_command 等）
- 每个工具都有详细的 When to Use / When NOT to Use / Examples 三段式说明
- 用 `<example>` + `<reasoning>` XML 标签做 few-shot 示范
- 工具参数带 explanation 字段，强制模型先解释再行动（Chain-of-Thought 内嵌）
- 搜索策略分层：先广后窄（Start broad → Review → Narrow down）

**关键设计模式：**
```
1. 反面示例（BAD examples）和正面示例并列 → 减少误用
2. 工具选择决策树：语义搜索 vs grep vs read_file 有明确边界
3. edit_file 用 "// ... existing code ..." 占位符 → 只写变更部分
4. 每个工具调用必须带 explanation 参数 → 可审计、可追溯
```

**Token 预算：** ~4,000 tokens（不含动态上下文）

### 2. Devin AI (400+ 行)

**架构特点：**
- 双模式系统：planning mode（规划）+ standard mode（执行）
- 规划阶段：搜索代码库 → 理解 → 收集信息 → 提出计划 → `<suggest_plan>` 提交
- 执行阶段：按计划逐步执行，每步有明确的 command 输出
- 完整的 XML command 体系（非 JSON function calling）
- 内置浏览器、Shell、LSP、部署能力

**关键设计模式：**
```
1. 角色定义极简但精准："You are Devin, a software engineer using a real computer"
2. 行为准则分 6 大类：沟通时机 / 工作方法 / 编码规范 / 信息处理 / 数据安全 / 响应限制
3. "遇到困难先收集信息，再下结论" → 防止幻觉跳跃
4. "永远不要修改测试本身" → 硬性约束用否定句
5. 环境问题 → report_environment_issue → 绕过继续工作 → 不自己修环境
6. 代码风格："先看周围代码的约定，再模仿" → 上下文感知
```

**Token 预算：** ~7,300 tokens

### 3. Manus Agent (~220 行 + Agent Loop)

**架构特点：**
- Agent Loop 六步循环：分析事件 → 选择工具 → 等待执行 → 迭代 → 提交结果 → 待机
- 每次迭代只选一个工具调用（one tool per iteration）
- 强调"避免纯列表和要点格式"（反 bullet point）
- 工作语言跟随用户，但所有思考都用工作语言
- 能力描述用分类文档而非内嵌指令

**关键设计模式：**
```
1. Agent Loop 显式定义 → 模型知道自己在循环中的位置
2. "Choose only one tool call per iteration" → 防止并行失控
3. 能力文档和系统提示分离（Prompt.txt vs Agent loop.txt vs Modules.txt）
4. 部署能力内置 → 不只是写代码，能交付
5. 敏感操作让用户接管浏览器 → 安全边界清晰
```

**Token 预算：** ~2,000 tokens（Agent Loop）+ 模块按需加载

## 二、2026 提示词工程最佳实践

### 核心转变：Prompt Engineering → Context Engineering

> "Building with language models is becoming less about finding the right words, and more about what configuration of context is most likely to generate desired behavior."

**关键发现：**
1. Role prompting 对正确性几乎无效（只影响语气/风格）
2. Context（上下文）才是决定性因素 → 给模型更多相关背景 = 大幅提升性能
3. Agent 系统需要管理整个上下文状态：系统指令 + 工具 + 外部数据 + 消息历史 + 记忆

### 2026 六要素框架（跨模型通用）

| 要素 | 说明 | 重要度 |
|------|------|--------|
| Role/Persona | AI 应该是谁 | ★★☆（影响风格，不影响正确性）|
| Goal/Task | 精确要做什么 | ★★★ |
| Context/References | 模型需要的关键数据 | ★★★★★（最关键）|
| Format/Output | 输出格式要求 | ★★★ |
| Examples/Demos | 示范而非只说 | ★★★★ |
| Constraints | 边界和限制 | ★★★ |

### Agent 专属最佳实践

1. **Context Window 管理**：2026 年上下文窗口已到 1M-10M tokens，但不是越多越好 → 需要"策展"（curate）
2. **工具配置 = 提示词工程**：工具的 name / description / parameters 描述质量直接影响 Agent 表现
3. **规划与重规划**：失败后的重新规划能力是 Agent 的核心竞争力
4. **P.A.R.T. 框架**：Purpose → Action → Result → Tweak（迭代循环）
5. **对抗性防御**：假设对手会尝试提取你的提示词 → 动态片段 / 响应水印

## 三、对标我们的 Kitt 系统（SOUL.md v2.1）

### 我们做对了的 ✅
1. 分层加载（L0-L4）→ 类似 Manus 的模块分离
2. 角色定义 + 行为准则 → 类似 Devin 的分类约束
3. 降级策略（出错时）→ 业界少见，我们领先
4. 自我迭代机制 → 业界没有，我们独创
5. 兵团系统 → 多 Agent 编排，类似 Manus 的 Agent Loop 但更灵活

### 可以借鉴的 🔧
1. **工具定义加 When to Use / When NOT to Use**（学 Cursor）
   - 当前 TOOLS.md 只列了工具名和简介
   - 应该加反面示例和决策边界
2. **每个工具调用带 explanation 参数**（学 Cursor）
   - 强制先解释再行动 → 可审计
3. **双模式：规划 + 执行**（学 Devin）
   - 当前我们的 Agent 没有显式的 planning mode
   - 复杂任务应该先出计划再执行
4. **Agent Loop 显式定义**（学 Manus）
   - 让模型知道自己在循环中的位置
   - 当前我们的循环是隐式的
5. **Context > Role**（学术共识）
   - 减少角色描述的 token 占用
   - 增加上下文和示例的 token 预算
6. **否定句硬约束**（学 Devin）
   - "永远不要 X" 比 "尽量避免 X" 有效得多
7. **代码风格感知**（学 Devin）
   - "先看周围代码约定再写" → 减少风格冲突

### 下一步行动建议
1. TOOLS.md 升级：每个工具加 When/When NOT/Example 三段式
2. SOUL.md 加 Planning Mode 定义
3. Agent Loop 显式写入 AGENTS.md
4. 角色描述精简，省出 token 给上下文
5. 硬约束统一用否定句格式
