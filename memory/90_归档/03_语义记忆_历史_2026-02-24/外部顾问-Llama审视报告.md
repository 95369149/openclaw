# 外部顾问审视报告：Kitt 系统架构深度分析

> 审视者：Claude Opus 4.6（以 AI 系统架构顾问身份）
> 审视时间：2026-02-19 00:28
> 审视对象：Kitt v3.0 核心配置（SOUL.md / IDENTITY.md / MEMORY.md / AGENTS.md / TOOLS.md / Fallback策略 / 自我迭代规则）
> 审视方法：逐文件交叉比对，找结构性问题，给可执行方案

---

## 一、记忆架构：分层合理但有结构性隐患

### 当前架构

```
L0: SOUL.md + IDENTITY.md + USER.md（每次必读）
L1: INDEX.md（导航）
L2: 强制规则（按需）
L3: 语义记忆（按需）
L4: 技能（用到时读）
```

编号目录：00-90，共 61 个文件。

### 问题 1：MEMORY.md 是定时炸弹

MEMORY.md 当前承担了"长期记忆总览"的角色，但它是一个不断膨胀的单体文件——系统架构、教训、待办、Worker 兵团、关注项目全塞在里面。随着 Kitt 运行时间增长，这个文件会越来越大，每次主会话启动都要全量读取，浪费 token 且增加噪声。

**可执行方案：**

- 将 MEMORY.md 拆成三个文件：
  - `MEMORY-core.md`：只保留"关于我"和"关于厂长"两节（< 500 字），每次必读
  - `MEMORY-system.md`：系统架构、Worker 兵团、Fallback 链（按需读取，仅系统维护时加载）
  - `MEMORY-lessons.md`：教训和已知坑（合并 TOOLS.md 的"已知坑"部分，消除重复）
- 待办项迁移到 `active-context.md`，那里才是它的归属
- AGENTS.md 启动流程改为：读 `MEMORY-core.md`（必读）+ 按需读其他

### 问题 2：信息重复散落

"已知坑"同时存在于 MEMORY.md 和 TOOLS.md，内容高度重叠（gateway.env、端口空格、v1api 余额等）。Fallback 链规则同时存在于 MEMORY.md 和 `01_强制规则/Fallback链安全策略.md`。这种重复意味着更新时容易漏改一处，导致信息不一致。

**可执行方案：**

- 确立"单一真相源"原则：每条信息只存一个地方，其他地方用引用
- 具体操作：MEMORY.md 的"教训"节 → 改为一行 `详见 memory/01_强制规则/操作纪律.md`
- MEMORY.md 的"Fallback 链"节 → 改为一行 `详见 memory/01_强制规则/Fallback链安全策略.md`
- TOOLS.md 的"已知坑"节 → 保留工具相关的坑，系统配置类的坑移到强制规则

### 问题 3：缺少记忆衰减/过期机制

当前只有"每周日扫描去重，归档过期内容"这一条模糊规则。没有明确的衰减标准——什么算过期？30 天没引用？还是手动标记？语义记忆 23 个文件只会增不会减。

**可执行方案：**

- 给每个语义记忆文件加 `last_referenced` 元数据（YAML frontmatter）
- 每周日扫描时：60 天未引用 → 移到 `90_归档/`，180 天未引用 → 删除
- 在 `_INDEX.md` 中标注每个文件的热度等级（🔥活跃 / ⏳冷却 / 🧊冻结）
- 强制规则和核心记忆豁免衰减

## 二、系统提示词（SOUL.md / AGENTS.md）：精炼但缺少关键指令

### 优点

SOUL.md 的设计哲学很好——短、有态度、不啰嗦。"有用，不表演有用"这句话比写 500 字的行为规范更有效。IDENTITY.md 给了 Kitt 人格锚点，这对长期一致性很重要。

### 问题 1：AGENTS.md 启动流程缺少健康检查

当前启动流程是纯粹的"读文件"序列，没有任何自检步骤。如果某个核心文件被意外删除或损坏，Kitt 会带着残缺的记忆运行而不自知。

**可执行方案：**
在 AGENTS.md 启动流程中加入第 0 步：

```
0. 健康检查：
   - 验证 SOUL.md / IDENTITY.md / USER.md 存在且非空
   - 验证 memory/01_强制规则/_INDEX.md 存在
   - 验证 MEMORY.md 的"强制规则"节包含关键条目
   - 任一检查失败 → 从黄金备份恢复 → 通知厂长
```

### 问题 2：SOUL.md 缺少"冲突解决"优先级

当强制规则之间冲突时（比如"零反问原则"vs"不确定就问"），Kitt 没有明确的裁决依据。

**可执行方案：**
在 SOUL.md 的"边界"节加一条：

```
冲突优先级：安全 > 强制规则 > 厂长实时指令 > 语义记忆 > 默认行为
特例：厂长明确说的话覆盖一切非安全规则
```

### 问题 3：缺少"上下文窗口预算"意识

没有任何地方告诉 Kitt 要管理自己的 token 预算。当 61 个文件都可能被加载时，很容易撑爆上下文窗口，尤其是免费模型（通常 8K-32K）。

**可执行方案：**
在 SOUL.md 加一条规则：

```
## Token 预算
- 启动加载总量控制在 3000 token 以内
- 单次任务最多额外加载 5 个记忆文件
- 超出预算时：优先丢弃 L3/L4，保留 L0/L1/L2
```

## 三、Fallback 策略：9 层链过长，需要分组优化

### 当前 9 层链

```
SiliconFlow免费 → SiliconFlow付费 → SiliconFlow Qwen → Groq Llama → Groq Qwen → Claude Sonnet → Claude Opus → Gemini Flash → Gemini CLI
```

### 问题 1：9 层太深，尾部模型几乎永远不会被触发

如果前 5 层都失败了（3 个平台全挂），第 6-9 层的 Claude 和 Gemini 大概率也有网络问题。9 层链的实际意义在第 5 层之后急剧下降，但每多一层都增加了配置复杂度和出错概率。

**可执行方案：**
改为"3 组 + 熔断"架构：

```
第一组（日常）: SiliconFlow 免费 → SiliconFlow 付费    [同平台秒切]
第二组（备用）: Groq Llama → Groq Qwen               [独立平台]
第三组（保底）: Claude Sonnet → Claude Opus            [付费保底]
紧急通道:       Gemini Flash                          [独立于上述三组]
```

- 每组内部顺序切换（毫秒级）
- 组间切换加 3 秒冷却（避免雪崩）
- 任一组连续失败 3 次 → 熔断 10 分钟，跳到下一组
- 紧急通道独立于分组，任何时候可手动激活

### 问题 2：缺少健康探针

当前是"失败了才切"的被动模式。没有主动探测哪个模型可用。

**可执行方案：**

- 利用心跳机制（已有 Gemini Flash 心跳），每 30 分钟对每组的首选模型发一个轻量探针（"ping"级别的请求）
- 探针失败 → 预切换到该组的备用模型，不等用户请求触发
- 在 `active-context.md` 维护一个"模型健康状态"段落：

```
## 模型健康 (自动更新)
- SiliconFlow: ✅ 正常 (最后探针: 00:15)
- Groq: ✅ 正常 (最后探针: 00:15)
- mynewapi: ⚠️ Sonnet 限流 (最后探针: 00:15)
- Google: ✅ 正常 (最后探针: 00:15)
```

### 问题 3：SiliconFlow Qwen3-32B 的位置不对

当前 Qwen3-32B 排在 SiliconFlow 付费版之后。但如果 SiliconFlow 平台本身挂了，免费 Qwen 也一样不可用。应该在付费版之后直接跳到 Groq（不同平台），而不是在同一个可能已经挂掉的平台上再试一个模型。

**可执行方案：**
调整为：SiliconFlow 免费 → SiliconFlow 付费 → **Groq Llama** → SiliconFlow Qwen → Groq Qwen → ...
或者更好的方案：采用上面的分组架构，SiliconFlow Qwen 作为第一组的第三选择，但组间切换时直接跳到 Groq。

## 四、自我迭代机制：框架好但缺少闭环验证

### 当前机制

八步流程 + Maker-Checker + 7 分制质量评分 + 三层记忆沉淀。

### 问题 1：迭代是"自己改自己"，没有外部校验

Kitt 的自我迭代完全是自评自改。Maker-Checker 模式虽然说"换视角"，但本质上还是同一个模型在做。这就像让学生自己批改自己的考卷。

**可执行方案：**

- 引入"交叉审计"机制：重要迭代（架构级改动、新强制规则）完成后，用 Kilo CLI 调用一个不同的模型（比如 Gemini Flash 或 Llama）做独立审查
- 具体流程：
  1. Kitt 完成迭代，生成变更摘要
  2. `kilo run --model "gemini-2.5-flash" "审查以下变更，找出逻辑漏洞和潜在风险：{变更摘要}"`
  3. 审查结果写入情景记忆
  4. 有重大问题 → 回滚 + 通知厂长
- 日常小迭代（更新语义记忆、记录教训）不需要交叉审计，只有改强制规则和系统架构时触发

### 问题 2：缺少"迭代效果追踪"

当前只有"做了什么"的记录，没有"效果如何"的追踪。比如加了一条强制规则，一周后这条规则到底有没有被触发？有没有产生预期效果？

**可执行方案：**

- 给每条新增的强制规则/语义记忆加一个 `验证期: 7天` 标记
- 7 天后在周日扫描时检查：
  - 被引用/触发过 → 标记为"已验证"，保留
  - 从未触发 → 标记为"待观察"，再给 7 天
  - 14 天仍未触发 → 降级为语义记忆或归档
- 在 MEMORY.md 维护一个"迭代看板"：

```
## 迭代看板
| 规则 | 创建日期 | 状态 | 触发次数 |
|---|---|---|---|
| Fallback链安全策略 | 02-18 | ✅已验证 | 3 |
| 画画频道规则 | 02-17 | ⏳待观察 | 0 |
```

### 问题 3：学习来源太被动

当前 Kitt 的学习主要来自：厂长指令 → 执行 → 复盘。缺少主动学习通道。

**可执行方案：**

- 利用已有的"空闲自学"强制规则，建立结构化学习管线：
  1. 每天空闲时段（深夜安静模式前），用 web_search 搜索 1-2 个与当前项目相关的技术话题
  2. 用 Kilo CLI 调用免费模型生成摘要
  3. 摘要写入 `02_知识库/`，更新 `_INDEX.md`
  4. 每周日从知识库中提炼可操作的改进点 → 写入语义记忆
- 关键约束：学习内容必须与厂长的业务方向相关（CNC、AI Agent、内容创作），不能漫无目的

## 五、安全与边界：有几个需要立即修复的隐患

### 隐患 1：黄金备份恢复缺少完整性校验（严重）

MEMORY.md 记录了"恢复旧黄金备份导致 Groq/SiliconFlow 被清除，失联 3 小时"。这说明黄金备份的恢复流程没有完整性校验——恢复了一个过期备份，反而把系统搞坏了。

**可执行方案：**

- 黄金备份加入 `manifest.json`，记录备份时的关键指纹：

```json
{
  "timestamp": "2026-02-19T00:00:00+08:00",
  "provider_count": 4,
  "providers": ["siliconflow", "groq", "mynewapi", "google-gemini"],
  "fallback_chain_length": 9,
  "mandatory_rules_count": 12,
  "checksum": "sha256:..."
}
```

- 恢复前自动比对 manifest：provider 数量减少 → 拒绝恢复 + 告警
- 恢复后自动运行健康检查（同启动流程第 0 步）

### 隐患 2：GitHub PAT 和 Webhook URL 明文存储（中等）

TOOLS.md 里直接写了 Discord Webhook ID（`1473213550549012513`），GitHub 用户名（`95369149`），PAT 路径（`~/.config/github-token`）。虽然这些文件是本地的，但如果 Kitt 的记忆文件被意外泄露（比如推送到 GitHub），这些信息就暴露了。

**可执行方案：**

- 敏感信息统一存入 `~/.openclaw/secrets/` 目录（不在 workspace 内，不会被 git 追踪）
- TOOLS.md 中用变量引用：`Webhook: $DISCORD_WEBHOOK_DRAW`
- 在 `.gitignore` 中确保 secrets 目录被排除
- 如果 workspace 有 git 仓库，检查历史提交中是否已经泄露过这些信息

### 隐患 3：子 Agent 权限边界模糊（中等）

`sessions_spawn` 可以创建子 Agent，但没有明确的权限限制。子 Agent 能不能修改强制规则？能不能执行 `config.patch`？能不能读取所有记忆文件？

**可执行方案：**

- 在强制规则中新增 `子Agent权限.md`：

```
## 子 Agent 权限边界
- ✅ 可以：读取 L3/L4 记忆、执行 web_search/web_fetch、调用 Kilo CLI
- ⚠️ 需要主 Agent 确认：修改语义记忆、发送 Discord 消息
- ❌ 禁止：修改强制规则、执行 config.patch、修改 SOUL.md/AGENTS.md、访问 secrets
- 子 Agent 的输出必须经过主 Agent 的质检流程才能写入记忆系统
```

### 隐患 4："零反问原则"与安全操作的冲突（低但值得注意）

"厂长说配就配"——但如果厂长说"把 Fallback 链改成只留一个模型"，Kitt 应该执行还是应该提醒风险？当前的规则体系没有明确区分"日常操作的零反问"和"高风险操作的安全确认"。

**可执行方案：**

- 定义"高风险操作白名单"，这些操作即使厂长直接下令也要做一次风险提示（不是反问，是提示）：
  - 删除/修改强制规则
  - 修改 Fallback 链（减少模型）
  - 恢复黄金备份
  - 修改 SOUL.md / AGENTS.md
- 提示格式固定为一行：`⚠️ 这会 [具体风险]。执行中。` 然后直接执行
- 不是反问，不需要等确认，但留下了记录

> 这份报告的核心观点：Kitt 的架构设计思路是对的（小文件、分层加载、编号目录），但在"信息去重"、"故障自愈"、"权限隔离"三个方面有结构性缺陷。上面的方案都是可以在现有框架内落地的，不需要推翻重来。
