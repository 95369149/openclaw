## 文章1: Claude Code 的 Prompt Caching 实战经验
**作者**: Thariq (Claude Code 团队)  
**来源**: https://x.com/trq212/status/2024574133011673516

### 核心理念
"Cache Rules Everything Around Me" —— Prompt caching 是 Claude Code 等长运行 Agent 产品的基础，通过复用计算显著降低延迟和成本。Claude Code 团队将整个系统架构围绕 prompt caching 设计，缓存命中率被视为核心指标，低于阈值会触发 SEV（严重事件）告警。

### 工作原理
Prompt caching 通过**前缀匹配**工作：API 缓存从请求开始到每个 cache_control 断点的所有内容。这意味着内容顺序至关重要——你希望尽可能多的请求共享相同的前缀。

### 最佳实践架构
**静态内容在前，动态内容在后**：
1. **Static system prompt & Tools**（全局缓存）
2. **Claude.MD**（项目内缓存）
3. **Session context**（会话内缓存）
4. **Conversation messages**（动态内容）

这种排序最大化了会话间的缓存命中率。

### 8个关键教训

#### 1. 布局系统提示词以优化缓存
- 静态内容在前，动态内容在后
- 避免在静态提示词中放置时间戳
- 不要随机打乱工具定义顺序
- 工具参数变更会破坏缓存

#### 2. 用系统消息更新信息
当信息过时时（如时间、文件变更），不要修改系统提示词，而是在下一轮对话中通过 `<system-reminder>` 标签传递更新信息。这样可以保留缓存。

#### 3. 不要在会话中切换模型
每个模型的缓存独立。即使在 100k tokens 的 Opus 会话中，切换到 Haiku 回答简单问题反而更贵，因为需要为 Haiku 重建缓存。

**解决方案**：用子 agent 切换模型，Opus 准备"交接"消息给另一个模型。Claude Code 的 Explore agents 就是这样用 Haiku 的。

#### 4. 永远不要在会话中添加/删除工具
这是最常见的缓存破坏方式。虽然直觉上应该只给模型当前需要的工具，但工具是缓存前缀的一部分，添加/删除工具会使整个会话的缓存失效。

#### 5. Plan Mode —— 围绕缓存设计功能
**错误做法**：进入 Plan Mode 时切换工具集为只读工具（破坏缓存）

**正确做法**：
- 始终保持所有工具在请求中
- 用 `EnterPlanMode` 和 `ExitPlanMode` 作为工具本身
- 用户切换 Plan Mode 时，agent 收到系统消息说明当前处于 Plan Mode 及指令
- 工具定义永不改变

**额外好处**：因为 EnterPlanMode 是工具，模型可以在检测到难题时自主进入 Plan Mode，无需破坏缓存。

#### 6. Tool Search —— 延迟加载而非删除
Claude Code 可以加载几十个 MCP 工具，全部包含在每个请求中会很贵，但在会话中删除它们会破坏缓存。

**解决方案**：`defer_loading`
- 发送轻量级存根（只有工具名 + `defer_loading: true`）
- 模型通过 ToolSearch 工具"发现"它们
- 只有在模型选择时才加载完整的工具 schema
- 缓存前缀保持稳定：相同的存根始终以相同顺序存在

#### 7. Forking Context —— Compaction（压缩）
当上下文窗口用尽时，需要总结对话并用摘要继续新会话。

**错误做法**：用不同的系统提示词和无工具的单独 API 调用生成摘要（缓存前缀完全不匹配，全价支付所有输入 tokens）

**正确做法**：Cache-Safe Forking
- 使用与父会话**完全相同**的系统提示词、用户上下文、系统上下文和工具定义
- 前置父会话的对话消息
- 在末尾追加压缩提示作为新用户消息
- 从 API 角度看，这个请求与父会话的最后一个请求几乎相同，缓存前缀被复用
- 唯一的新 tokens 是压缩提示本身

**代价**：需要保留"压缩缓冲区"，在上下文窗口中留出足够空间容纳压缩消息和摘要输出 tokens。

#### 8. 监控缓存命中率
- 像监控正常运行时间一样监控缓存命中率
- 设置告警，缓存破坏视为事件
- 几个百分点的缓存未命中率会显著影响成本和延迟

### 对制造业管理的启示

#### 1. 流程稳定性优先
就像 prompt caching 要求稳定的前缀顺序，企业流程也需要稳定性：
- **标准化操作流程**：频繁变更流程会增加培训成本和出错率
- **工具集固定**：不要频繁更换设备或软件，保持工具链稳定
- **分层缓存思维**：全局标准（如质量标准）→ 项目标准（如客户特殊要求）→ 会话标准（如当班注意事项）

#### 2. 信息更新策略
不要修改核心文档，而是通过"补充通知"传递更新：
- **核心制度不轻易改**：用"补充通知""临时规定"传递变更
- **保留历史版本**：方便追溯和回滚
- **增量更新而非全量重写**：降低学习成本

#### 3. 角色切换成本
就像模型切换会破坏缓存，人员频繁换岗也有高昂成本：
- **减少不必要的岗位轮换**：除非有明确的培养目的
- **用"子任务"而非"换人"**：遇到专业问题，请专家协助而非换人
- **交接要"缓存友好"**：新人接手时，提供完整的上下文和工具集

#### 4. 工具集管理
永远不要在项目中途添加/删除工具：
- **项目启动前确定工具清单**：中途加工具会打乱节奏
- **用"延迟加载"思维**：准备备用工具但不强制使用
- **工具培训前置**：不要等到需要时才学

#### 5. 监控关键指标
像监控缓存命中率一样监控企业效率：
- **流程执行率**：标准流程的遵守比例
- **返工率**：类似缓存未命中，返工是最大的成本浪费
- **工具利用率**：设备和人员的有效使用时间

### 可落地的管理动作
1. **建立"流程缓存"机制**：标准化常见操作，减少重复决策
2. **设置"流程破坏"告警**：当有人偏离标准流程时，系统提醒
3. **优化交接流程**：确保新人接手时有完整的"缓存前缀"（背景信息）
4. **工具集审计**：定期检查是否有不必要的工具变更

## 文章2: AI 生图构图技巧 - 镜面倒影构图
**作者**: VoxCat  
**来源**: https://x.com/voxcatai/status/2024476823141437478

### 核心理念
为什么一个水洼就能让普通街拍变成「大片」？因为倒影让画面信息密度翻倍，同时地平线天然把画面切成对称的两个世界。

### 核心公式
**镜面载体 + 分割线 + 虚实反差**

### 三个核心组件

#### 1. 镜面载体 (Mirror Surface)
水面、湿地面、抛光石板、玻璃、金属——任何能反射的平面。

#### 2. 分割线 (Divider)
反射面边缘形成天然水平线，把画面分为「实体」和「倒影」两层。

#### 3. 虚实反差 (Real vs. Reflection)
实体清晰，倒影微变形、微模糊、色温偏移——这层差异就是「诗意」的来源。

### 四级反射系统（关键！）

**不指定级别的话 AI 会随机给，所以一定要锁定。**

- **L1 完美镜面** = `mirror-like reflection, perfect symmetry`
  - 上下几乎完全对称，仪式感拉满

- **L2 清晰倒影** = `clear reflection, wet-look polished surface`
  - 轮廓清晰但有轻微波纹

- **L3 模糊倒影** = `soft blurred reflection, subtle ripples`
  - 倒影朦胧化，诗意最强

- **L4 碎片倒影** = `fragmented reflection, broken surface`
  - 倒影不完整，心理张力/奇幻感

### 五个进阶技巧

#### 1. 色温分离
实体偏暖（日光），倒影偏冷（水面吸暖色后偏蓝灰）。
- 提示词：`reflection with cooler color temperature shift`

#### 2. 焦平面分离
实体锐，倒影柔。这是「专业感」和「手机感」的分水岭。
- 提示词：`Sharp focus on real subject, reflection slightly soft-focus`

#### 3. 涟漪叙事
静止画面中的唯一运动源，倒影「正在被打破」的瞬间感。
- 提示词：`a single water drop creating ripple rings in the reflection`

#### 4. 倒影 x 低机位联动
机位降到接近反射面，倒影面积指数级增长。
- 提示词：`Camera angle at ground level, nearly touching the reflective surface`

#### 5. 倒影 x 框中框联动
倒影本身就是天然的「框」——在倒影中再加入拱门/窗格，形成「倒影里的框中框」，层次叠加。

### 避坑指南

❌ **倒影面积太小** → 至少占画面 30%  
❌ **虚实完全一样** → 必须加虚实差异（模糊/色温/波纹），否则 AI 会当成图片翻转  
❌ **分割线不清晰** → 水面/地面分割线保持干净连贯  
❌ **忘记指定反射率** → 用 L1-L4 锁定，不写就随机

### 跟其他构图的区别和联动

- **vs 三段分层**：三段是「从前到后看深度」，倒影是「从上到下看对称」
- **低机位**：倒影面积翻倍
- **框中框**：倒影内再构框
- **负空间**：水面天然就是大面积留白

### 速记公式
**镜面倒影 = 镜面载体 + 分割线位置 + 反射级别(L1-L4) + 虚实差异**

### 对制造业管理的启示

#### 1. 系统化方法论
- **标准化操作**：用 L1-L4 这样的分级系统锁定质量标准
- **避免随机性**：不指定级别就随机，不制定标准就混乱
- **可复制的流程**：把经验转化为可执行的公式

#### 2. 细节决定品质
- **量化标准**：倒影面积至少30%，类似"合格率至少95%"
- **必要的差异**：虚实差异是诗意来源，类似"标准化中的个性化"
- **清晰的边界**：分割线清晰，类似"责任边界明确"

#### 3. 视觉营销应用
- **产品摄影**：用镜面倒影构图提升产品照片的专业感
- **品牌宣传**：用 L1-L4 反射系统打造视觉记忆点
- **展会布置**：利用镜面材质和灯光营造高级感

### 可落地的营销动作
1. **产品拍摄标准化**：建立镜面倒影构图的拍摄 SOP
2. **展厅设计优化**：增加镜面元素（抛光地面、玻璃展柜）
3. **社交媒体内容**：用倒影构图提升视觉冲击力

## 文章3: Miles Deutscher 的 Claude Code Prompt 架构
**作者**: 阿绎 (AI进化论) 转述 Miles Deutscher  
**来源**: https://x.com/ayi_ainotes/status/2020345793098707305

### 核心理念
**用组织管理逻辑驾驭 AI，而不是指令逻辑**

### 4个核心模块
1. **Role Definition (角色升维)**：从 Coder 升级为 Technical Co-Founder，负责技术决策和挑战假设
2. **Process Control (流程锁定)**：强制分阶段（Discovery → Planning → Building），防止 AI 一上来就瞎写
3. **Communication Protocol (沟通协议)**：讲人话（plain language）+ 决策权归属（keep me in the loop）
4. **Anti-Fragile (反脆弱)**：预设边缘案例处理、要求生产级质量（Not a hackathon project）

### 核心心法
**先花 80% 的篇幅教 AI 怎么做个好员工**：
- 敢于质疑老板（Challenge assumptions）
- 做事有章法（Discovery → Planning → Building）
- 凡事有交代（Stop and check in）

### 管理启示（重点！）
这套 Prompt 架构完全可以迁移到企业管理：

1. **角色升维**：不要把员工当"执行者"，而是当"合伙人"
   - 给予技术决策权
   - 鼓励挑战假设和提出质疑
   - 培养主人翁意识

2. **流程锁定**：强制分阶段执行，防止"一上来就干"
   - Discovery（调研）→ Planning（规划）→ Building（执行）
   - 每个阶段有明确的交付物和检查点
   - 类似九大机制中的"流程标准化"

3. **沟通协议**：明确沟通规范
   - 讲人话，不讲黑话（避免信息不对称）
   - 决策权归属清晰（谁拍板、谁执行、谁监督）
   - 类似"凡事有交代、件件有着落、事事有回音"

4. **反脆弱**：预设边缘案例，要求生产级质量
   - 不是"能跑就行"，而是"能扛住压力"
   - 预设异常场景和应对方案
   - 类似"军令状"机制中的风险预案

### 可落地的管理动作
- **改造岗位说明书**：从"执行者"升级为"负责人"
- **优化工作流程**：强制分阶段（调研→规划→执行→复盘）
- **建立沟通协议**：每周例会、每日站会、关键节点汇报
- **设置质量红线**：不接受"差不多就行"，要求生产级交付
