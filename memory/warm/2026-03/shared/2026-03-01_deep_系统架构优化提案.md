# 系统架构优化提案（deep）

- 时间戳：2026-03-01 14:49 GMT+8
- 审查范围：`.abstract`、`01_强制规则/排兵布阵.md`、`HEARTBEAT.md`
- 评估目标：识别流程瓶颈、冗余设计、单点故障，并给出可落地改造方案

## 第一章：现状结构与运行画像

### 1.1 当前拓扑（依据权威文件）
- **组织结构**：`jimmy(L0)` 单入口调度；`deep/logic/main(L1)` 执行；`kitt(L2)` 架构决策。
- **规则层级**：`排兵布阵.md` 是 agent 编制、路由、fallback 的唯一权威；`.abstract` 作为速查摘要；`HEARTBEAT.md` 负责巡检与轻量修复。
- **任务面板**：`task-board.json` 管 active/ready/completed，理论上由 jimmy 维护状态迁移。

### 1.2 当前优势
- 单入口决策降低了多头指挥冲突。
- 已有“失败降级链 + 最多重试2次 + 禁止静默失败”意识，治理方向正确。
- 心跳机制明确区分“可自动修复”和“不可自动修复”，安全边界清晰。

### 1.3 当前隐含代价
- 文档中存在多个“关键控制点”集中在 jimmy 与心跳，易形成拥塞。
- 规则在多个文件重复（权威/摘要/心跳）后，维护成本上升，漂移风险增大。

## 第二章：关键问题诊断（瓶颈 / 冗余 / 单点）

### 2.1 流程瓶颈

#### 问题 A：jimmy 过载（调度+外部碰撞+记忆管理+配置变更）
- 在 `排兵布阵.md` 中，jimmy 同时承担：意图路由、简单任务直做、浏览器操作、外部碰撞、记忆与配置管理。
- 这会造成**调度控制面和业务执行面耦合**：一旦 jimmy 被复杂请求占用，派单与状态同步都会延迟。

**影响**：
- 子 agent 结果回收慢，`task-board` 状态易滞后。
- 心跳和主会话都依赖 jimmy 时，突发任务高峰下响应抖动。

#### 问题 B：心跳职责过宽（巡检+修复+任务校对+provider ping）
- `HEARTBEAT.md` 把“状态观测”和“状态修复”绑在同一流程里，且每轮都可能触发多项检查。
- 心跳一旦执行异常或被跳过，多个子系统（sync/task/provider）会同时失去兜底。

**影响**：
- 心跳本身成为高耦合任务，失败时故障面扩大。

### 2.2 冗余设计

#### 问题 C：规则重复定义导致漂移风险
- `.abstract`、`排兵布阵.md`、`HEARTBEAT.md` 都写了编制、流程、状态规则。
- 虽声明“以排兵布阵为准”，但摘要仍承载大量执行性信息，且需手工同步。

**影响**：
- 文档更新靠人工，极易出现“配置已变更、摘要未更新”。
- 新 agent/新流程上线时，审核成本高。

#### 问题 D：任务状态来源多点更新
- 规则描述中存在 `jimmy`、`heartbeat` 都可能更新 `task-board.json`。
- 若没有统一“状态写入锁/版本号”，并发写入可能产生回退或覆盖。

**影响**：
- active/done/failed 可能短暂不一致，影响后续调度判断。

### 2.3 单点故障

#### 问题 E：调度单点（L0 仅 jimmy）
- 单入口是优点，但也意味着 jimmy 不可用时，全局调度停摆。

#### 问题 F：高价值任务依赖高延迟 agent（kitt）
- `排兵布阵.md` 明示 kitt“慎用 + xjrouter 延迟高，偶有超时”。
- `task-board.json` 已出现 `SYS-01`（架构审查）失败案例，说明风险非理论。

**影响**：
- 关键决策任务有超时概率，影响管理层节奏。

#### 问题 G：运维观测单源（ops/state.json）
- HEARTBEAT 依赖 `ops/state.json` 判断巡检和同步健康。
- 若状态文件写入失败/损坏，心跳可能误判系统状态。

## 第三章：优化方案（可落地）

### 3.1 架构拆分：控制面 / 执行面解耦

**建议 1：将 jimmy 从“执行参与者”收敛为“纯调度控制面”**
- 保留：意图识别、派发、验收、升级仲裁。
- 下放：
  - 浏览器/外部碰撞优先下发给 deep/main（jimmy 只在冲突或关键判断时介入）。
  - 记忆整理、批量文件治理交给 deep。

**预期收益**：
- 降低 jimmy 平均占用时长，提升派单吞吐。
- 减少“主会话任务堵住全局调度”的概率。

### 3.2 状态机治理：统一 task-board 写入协议

**建议 2：建立 task-board 状态机（单写者 + 版本号）**
- 明确单写者：默认仅 jimmy 写状态；heartbeat 只写 `ops/state.json`，不直接改 task-board。
- 引入版本戳：每次写入 `task-board.json` 增加 `version` 或 `updatedAt`，写前校验。
- 固化迁移：`ready -> active -> done/failed`，禁止跨级跳转。

**预期收益**：
- 降低并发覆盖、状态回退、脏写问题。
- 审计链更清晰，问题更可追溯。

### 3.3 文档治理：权威源 + 自动生成摘要

**建议 3：把 `.abstract` 从“手写执行规则”改成“自动生成速览”**
- 保留 `.abstract` 的导航功能，但不承载需人工同步的硬规则。
- 由脚本从 `排兵布阵.md` 抽取 agent 编制、路由和fallback摘要（定时或变更时生成）。
- HEARTBEAT 只保留“执行动作清单”，不重复 Agent 编制细节。

**预期收益**：
- 降低文档漂移风险。
- 更新成本从“多文件手工一致性”降到“单源更新 + 自动派生”。

### 3.4 关键链路冗余：L0 与高风险任务降级

**建议 4：建立“L0应急接管”机制**
- 预定义 `main` 作为临时调度代理（仅在 jimmy 不可用时启用最小路由规则）。
- 路由策略简化：无法判定时一律派 deep，避免系统停摆。

**建议 5：kitt 任务前置分级**
- 只有“必须战略决策”才进 kitt；其余架构评审先由 deep 出初稿，再按需升级 kitt。
- 为 kitt 任务设置 2 段式超时（如 3min 软超时提示 + 8min 硬超时降级）。

**预期收益**：
- 降低关键任务受单模型延迟影响。
- 将“全失败”转化为“降级可交付”。

### 3.5 心跳瘦身：从全能巡检改为分层巡检

**建议 6：心跳只做轻观测，修复动作下沉到专用脚本/cron**
- 心跳读取状态 + 告警，不做多项主动修复（避免心跳执行路径过重）。
- `sync`、`provider ping`、`task reconcile` 分离为独立 cron，心跳只汇总结果。

**预期收益**：
- 缩短心跳执行路径，降低失败半径。
- 巡检异常定位更直接（哪条 cron 出问题一目了然）。

## 第四章：实施路线图（两周）

### 第 0-2 天：止血与可观测性
1. 锁定“task-board 单写者= jimmy”规则，heartbeat 暂停写 task-board。
2. 给 task-board 增加 `updatedAt` 字段，所有写入必须刷新。
3. 在 ops/state.json 增加三个独立健康位：`syncOk`、`providerPingOk`、`taskReconcileOk`。

### 第 3-7 天：解耦与自动化
4. 抽离 `.abstract` 生成脚本：从 `排兵布阵.md` 自动导出 Agent 编制与路由摘要。
5. 把 heartbeat 中修复动作迁移到 cron（按职责拆 2-3 条小任务）。
6. 把 jimmy 的“可下放任务”清单落地（浏览器批量抓取、内容批处理优先派发 deep/main）。

### 第 8-14 天：冗余与演练
7. 建立 L0 应急接管 runbook（jimmy 不可用时 main 临时调度）。
8. 进行一次“kitt 超时演练”与一次“ops/state 缺失演练”，验证降级链是否可用。
9. 复盘并更新 `排兵布阵.md` v5.1，删除过期规则。

## 第五章：量化验收指标（建议）

- **调度时延**：jimmy 首次派单中位时延 < 5s。
- **状态一致性**：task-board 非法状态迁移次数 = 0。
- **降级可交付率**：子 agent 失败后 10 分钟内给出替代结果比例 > 95%。
- **文档一致性**：`排兵布阵.md` 与 `.abstract` 关键字段一致率 100%（自动校验）。
- **心跳稳定性**：心跳执行失败率 < 1%，且失败不影响核心任务推进。

---

## 结论
当前体系方向正确（单入口+明确编制+降级意识），但已出现“**控制面过载、状态写入多点、文档手工同步、关键链路单点**”四类典型规模化问题。建议按“先止血（状态一致性）→再解耦（控制/执行分离）→后冗余（L0应急与演练）”推进。若按两周路线执行，可显著降低任务卡死与规则漂移风险，并提高厂长层面的决策交付稳定性。
