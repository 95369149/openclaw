# Lyra 外部调用优化建议

- 时间：2026-03-06 19:29 GMT+8

## 现状评估
当前 Lyra 适合“人工交互式编译提示词”，不够适合手机端/第三方 app 直接投喂。优点是原则清晰、模式完整、视觉协议强；问题是篇幅长、分支多、默认先追问、含大量方法论与进化说明，作为外部调用 system prompt 成本偏高，稳定性也容易受上下文长度和宿主 app 能力影响。

## 问题清单
1. 单体过长：把身份、方法论、教程、模板、版本史全塞一起，外部 app 首轮 token 浪费大。
2. 交互依赖强：默认“先问再写”适合聊天，不适合 API 一次调用。
3. 宿主不友好：`/evolve`、`/audit`、Skill 加载、联网刷新等，对多数外部 app 不可执行。
4. 模式混杂：文本/代码/分析/视觉/Agent/风格共存，导致指令焦点不够硬。
5. 输出结构偏重：XML 全量模板对移动端和轻量调用偏厚。

## 推荐结构
建议拆成三层：
1. 系统提示词版（Core）：保留身份、核心原则、输出纪律、少量模式路由，控制在 300-500 字，作为所有外部调用底座。
2. API 调用版（Runtime）：在 Core 上补“输入槽位+降级规则+是否允许追问+无补充信息时直接产出最优版”，适合 n8n、Dify、AppScript、第三方壳应用。
3. 移动端精简版（Mobile）：只保留“识别任务→必要时最多追问1次→直接给可复制结果”，去掉 changelog、进化协议、长模板、工具链说明。

再做版本矩阵：
- Lyra-Core：统一底座
- Lyra-Mobile：短、稳、低 token
- Lyra-API：结构化输入输出
- Lyra-Visual：单独承接图片/视频生成
- Lyra-Pro：保留完整版，给 Claude/Gemini/OpenClaw 内部长上下文场景

## 下一步实施建议
先不要继续堆大一统 PROMPT.md，而是新增 4 个对外版本文档；统一共享同一套原则，但拆掉不可执行模块。优先先做 Lyra-Mobile 与 Lyra-API，两者最能解决“外部 app 直接调用”和“稳定打到厂长要求”。同时补一份调用规范：输入字段、默认补全策略、追问阈值、输出模板。这样 Lyra 才能从“高手手动用得爽”，升级成“外部系统稳定可调”。
