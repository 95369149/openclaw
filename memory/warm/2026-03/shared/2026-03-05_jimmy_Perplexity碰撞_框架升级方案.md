## 核心判断
"这是一个典型的「架构债务叠加」问题，五个改进点背后有三条主线根因。"

---

## 七个痛点根因分析

**①工具调用次数限制 vs 外链读取**
根因：策略冲突源于单一限制规则试图同时管控「防循环」和「防超时」两个不同目标。规则设计粒度太粗，对「写代码」和「浏览网页」用了同一个token配额。

**②logic和kitt职责模糊**
根因：角色定义沿「能力维度」划分，而非「决策权维度」划分。战略推演本身就包含决策，架构审核本身就需要深度推理。jimmy路由时无法找到明确的if-then判断依据，变成概率猜测。

**③子agent写文件成功率<30%**
根因：原子性缺失 + 输出缓冲区没有检查点。子agent被要求在单次调用中「推理+生成内容+调用写文件工具」，token逼近限制时模型在生成阶段截断，写文件的tool call根本没被执行到。这是**事务性操作被分散在单次非事务性LLM调用中**的典型失败。

**④jimmy上下文污染**
根因：调度层承担了不该承担的「执行历史」负担。这是学术文献中明确命名的**「无界上下文积累反模式」（Unbounded Context Accumulation Anti-Pattern）**——上下文随执行步数线性增长，最终超过模型有效注意力窗口。

**⑤记忆系统碎片化**
根因：记忆系统是按「工具可用性」而非「访问模式」演化出来的。没有区分「热记忆」（高频访问）和「冷记忆」（低频归档），所有机制都要在每次prompt注入时扫描。

**⑥心跳每55分钟消耗大量token**
根因：心跳设计目的是「保活」，但实现方式是「完整LLM推理」。把「连接保持」的基础设施问题，错误地用一次完整的agent调用来解决。

**⑦deep的Responses API协议不匹配**
根因：多模型集成时缺少协议适配层（Protocol Adapter Layer）。jimmy把所有子agent视为同一接口调用，但OpenAI Responses API和标准Chat Completions API在消息结构、工具调用格式、流式响应上都有差异。

## A-E 明确建议

**A. logic和kitt合并** ✅
合并，但用「触发条件」重新定义，而非「能力标签」：
- 合并后命名为 `sage`（claude-opus或thinking系列）
- 触发规则：凡是需要超过2步逻辑链、或结果将影响不可逆操作（资金、人事、架构变更）的任务，统一派给sage
- kitt当前的「慎用」标签说明它本质上是高成本安全阀，合并后用`[REVIEW_REQUIRED]`标记触发同等效果

**B. 子agent只返回文本，jimmy统一写文件** ✅
重试机制治标不治本——token耗尽是确定性的资源限制。正确方案：
- 子agent**只返回结构化JSON**（`{"filename": "...", "content": "..."}`），不调用任何文件工具
- jimmy收到响应后做写文件操作
- 在子agent的system prompt中加硬性约束：「你的最终输出必须是JSON，否则视为任务失败」

**C. 记忆系统精简到三层** ✅
| 层级 | 对应内容 | 更新频率 | 注入时机 |
|------|---------|---------|---------|
| 长期事实层 | 老板偏好、公司信息、常用规则 | 手动/周级 | 每次jimmy启动时全量注入 |
| 任务状态层 | 当前进行中任务、task-board | 每轮更新 | 按需注入（相关任务时）|
| 临时数据层 | 单次会话的中间结果 | 会话结束即丢弃 | 不注入，仅在内存中流转 |

原来的MEMORY.md + .abstract + shared目录合并进长期事实层；task-board留在任务状态层；每日日志降级为仅归档，不参与上下文注入。

**D. 引入上下文压缩+摘要接力（非硬性轮换）** ✅
硬性轮换会丢失对话连续性。更好方案：
- 设定**上下文水位线**（如60% context使用率触发压缩）
- 触发时jimmy调用`summarize_session`工具，把历史压缩成结构化摘要追加到任务状态层
- 新轮次从摘要重启，而非完整历史

**E. 心跳降频+改变实现方式** ✅
仅降频是治标。更优方案：
- 心跳从「完整LLM调用」改为**「轻量级状态检查脚本」**（不调用LLM，只写时间戳到状态文件）
- 真正的LLM心跳降至**2-4小时一次**
- 结合D的上下文压缩，心跳时顺带触发一次压缩

## TOP3 优先改造项

**🥇 第一优先：修复子agent写文件（痛点③）**
影响最直接，<30%成功率意味着系统核心功能不可靠，其他一切优化都建立在沙滩上。
具体做法：
- 在所有子agent的system prompt末尾加：`【输出规则】若任务要求生成文件，你必须以如下JSON格式作为最终输出：{"task_id": "...", "filename": "...", "content": "...", "status": "done"} 任何情况下不得直接调用文件写入工具。`
- jimmy的响应处理逻辑加JSON解析模块，检测到上述格式时自动执行写文件
- 加写入验证回调（写完后读一行确认文件存在）

**🥈 第二优先：解决jimmy上下文污染（痛点④）**
长期运行质量退化是慢性病，不解决会让所有其他agent的表现被拖累。
具体做法：
- 子agent的完整返回内容**不追加到主对话历史**，只提取结构化结果（`{"result_summary": "...", "files_written": [...], "next_action": "..."}`）
- 设置context使用率监控，超过55%时触发：调用deep生成会话摘要 → 写入任务状态层 → jimmy以摘要重新初始化
- jimmy的system prompt中「任务执行历史」部分替换为「任务完成状态表」（只记录done/pending/failed，不记录过程）

**🥉 第三优先：统一deep的协议适配（痛点⑦）**
低垂的果实，一次性投入消除未来所有与deep交互的不稳定性。
具体做法：
- 为deep单独封装一个**协议适配包装器**（wrapper function），对外暴露与其他agent完全相同的调用接口
- 包装器内部处理Responses API的格式转换、tool_call字段映射、流式转标准输出
- jimmy调用所有agent时走统一接口，协议差异完全封装在wrapper内

## 架构改造路线图

```
第1周 修复子agent写文件（JSON返回 + jimmy统一写）
第2周 deep协议适配层上线
第3周 logic+kitt合并为sage，更新jimmy路由规则
第4周 jimmy上下文水位监控 + 压缩机制上线
第5-6周 记忆系统三层重构 + 心跳轻量化改造
```

logic/kitt合并放第3步而非第1步：需要对jimmy的路由逻辑做较大改动，建议在写文件和协议问题稳定后再动。
记忆系统重构放最后：迁移成本最高，应在系统其他部分稳定后做一次性迁移。
