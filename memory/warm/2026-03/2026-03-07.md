- **Lyra 提示词体系升级为外部调用标准 v2.0**：厂长需求明确，Lyra 不应是越写越长的单一 prompt，而应成为可被不同 App（豆包、Dify、Coze 等）稳定调用的版本矩阵。已落地核心文件升级，剥离理论与冗余，直接提供确定性结构输出。

- **生成复杂排版图片不再使用浏览器截图服务代理**：在给厂长生成“明天加班安排表”图片时，因将浏览器本地临时网页(127.0.0.1)作为媒体链接发给 Telegram，导致厂长手机和电脑端均报拒绝连接错误。改为使用 Python `PIL` 库直接渲染本地真实 PNG 图片（存至桌面），避免了复杂的内外网穿透和截图插件文件传输壁垒。

## 3. 经验教训
- 当底层 API provider 表现不稳定（如超时、被拒绝）叠加错误的 API 接口类型（`openai-responses`）时，系统表面看起来在线，实际无法执行任何写入或规划操作。对于需要执行落地文件写操作的主力通道，必须采用最稳定的 `openai-completions`。
- 外部 App 调用 AI Agent 时最怕“无界追问”和“格式抽风”。对于轻量级/自动化 API 模式，必须要求 AI 在信息不完整时先基于常识给出临时最优执行版（Default to do），只在极端关键时才追问 1 个问题，绝不能卡住等待（Default to ask）。
- 新模型配置后若测试遇到第一层阻断 (`model not allowed`)，不要盲目排查网络，应优先检查 OpenClaw `agents.defaults.models` 白名单是否已同步放行该模型。
- **中转 API 模型造假识别**：测试切换到 `mynewapi/claude-opus-4-6` (`opus` 模型别名) 时，发现该中转节点“挂羊头卖狗肉”，实际响应由 Google Gemini 生成。已识别并提醒厂长，若需真实 Opus 推理能力，需切换至如 `xjrouter` 节点。
- **Message 工具发送本地图片边界情况报错**：使用 `message` 工具以本地路径发送图片文件给 Telegram 时，工具校验参数报错提示 `Use target instead of to/channelId`，存在适配问题。针对类似需求当前推荐直接写到 Desktop 供厂长自提。
