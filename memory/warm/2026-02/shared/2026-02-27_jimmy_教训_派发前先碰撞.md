# 教训：派发任务前先做外部碰撞

日期：2026-02-27
来源：厂长反馈

## 问题
P01/P02/P04 三个任务直接派给 deep，没有先用 web_search/web_fetch 做外部调研，导致子 agent 只能基于内部知识闭门造车。

## 正确做法
1. 派发前先用 web_search 搜集行业最新信息、竞品案例、最佳实践
2. 把调研结果作为背景信息写入 task 描述
3. 需要深度调研的任务，先碰撞再派发

## 适用场景
- 行业调研类任务
- 竞品分析类任务
- 方案设计类任务（需要了解当前市场/技术现状）
- 内容创作类任务（需要参考同行爆款）

## 不需要碰撞的场景
- 纯内部操作（配置修改、文件整理）
- 已有充足背景信息的任务
- 简单问答

# 教训2：成本优先原则没执行

日期：2026-02-27
来源：厂长痛骂

## 问题
P01/P02/P03/P04 全派给 deep（付费），但这些都是"写中文方案文档"类任务，main（Gemini 免费）完全能干。浪费钱。

## 正确做法
- 方案设计、内容策划、文档撰写 → main（免费）
- 代码开发、批量处理、多步推理 → deep
- 数学/算法/性能优化 → logic
- 架构决策、战略规划 → kitt（慎用）

## 派发前必问自己
1. 这个任务 main 能不能干？→ 能就给 main
2. main 干不了的原因是什么？→ 说不出来就给 main
3. 只有明确需要代码/推理/批量才给 deep

# 教训3：让子 agent 自己搜外链

日期：2026-02-27
来源：厂长再骂

## 问题
jimmy 自己搜了一轮外链，把结果当背景塞进 task 描述。但子 agent 也有 web_search/web_fetch 工具，应该让它们自己搜、自己验证、边搜边写。

## 正确做法
每次派发 task 必须加这段：
"请大量使用 web_search 和 web_fetch 做实时调研，先搜后写，所有数据必须来自实时搜索验证，不要凭记忆编造。"

## 为什么
- web_search/web_fetch 免费，子 agent token 要花钱
- 让子 agent 搜到真数据再写，质量高、token 省（不用瞎编再改）
- jimmy 搜一轮只能给摘要，子 agent 自己搜能深入细节
