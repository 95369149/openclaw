## 1. sino / deep 分工矩阵

### 1.1 路由原则

- **sino**：中文表达质量优先，适合文案、润色、翻译、本地化表达
- **deep**：技术正确性优先，适合代码、脚本、自动化、复杂推理
- **组合链**：`deep → sino` 用于"技术内容先做对，再做顺"

### 1.2 决策矩阵

| 维度 | 给 sino 的条件 | 给 deep 的条件 |
|------|----------------|----------------|
| 写作 | 纯中文文案、营销页、公众号稿、销售话术 | 技术方案、API 文档、README、含大量代码片段的技术长文 |
| 代码 | 仅中文注释/报错/提示语改写 | 实际写代码、调试、重构、脚本/自动化 |
| 分析 | 需要用中文讲故事、包装结论 | 需要严谨技术细节、复杂推理、多步计划 |
| 翻译 | 英文/多语种 → 高质量中文，对外展示 | 中英互译中带大量技术术语/代码注释 |
| 润色 | 已有中文内容做流畅度、说服力、风格统一 | 含技术细节的文档要同时做逻辑结构与技术校正 |
| 输出长度 | 1 段文案到约 3–4 千字文章，重点在语言质量 | 超长技术文档、目录化说明、多模块方案 |
| 是否需要联网搜索 | 不需要，或已有 scout 提供素材 | 需要综合外部技术资料/官方文档/issue |
| 中文质量要求 | 营销级 / 文学级 / 品牌调性一致 | 技术准确优先，文风可稍硬 |
| 是否涉及代码/技术 | 仅少量变量名或示例 | 需要写/改函数、接口、脚本 |
| 上下文长度需求 | 处理中等上下文即可 | 需结合多份技术文档与历史决策 |

### 1.3 典型 case

1. **新品发布会邀请函** → `sino`
   - 目标是转化率和文案质感，不是技术准确性。

2. **为新 API 写 README + 示例代码** → `deep`
   - 核心是技术正确性与代码可运行；如需更顺的中文，再 `deep → sino`。

3. **英文白皮书转公众号综述** → `main → scout（如需）→ sino`
   - 长文理解先交给 `main`，外部补证据给 `scout`，最终面对公众的中文稿交给 `sino`。

4. **分析 Python 脚本 bug 并修复** → `deep`
   - 这是纯技术执行与代码推理任务。

5. **前端组件库中文文档统一语气** → `deep → sino`
   - 先由 `deep` 保技术结构，再由 `sino` 做营销向润色与风格统一。

## 2. FAST / FULL 路由

### 2.1 FAST 链

适用条件：
- `riskLevel = LOW`
- `size = SMALL`
- 不命中强制侦察条件
- 不涉及高风险配置与对外正式输出

默认路径：
- 中文内容：`jimmy → sino → jimmy`
- 小型技术改动：`jimmy → deep → jimmy`
- 单纯多模态读取：`jimmy → main → jimmy`

### 2.2 FULL 链

适用条件：
- 命中任一强制侦察条件
- `riskLevel ≥ MEDIUM`
- 需要对外正式交付
- 涉及配置、规则、架构、跨文件改动

默认路径：
- 研究型：`jimmy → scout → deep/sino/main → guard（如需）→ kitt（如需）→ jimmy`
- 配置型：`jimmy → scout（如需）→ deep → guard → kitt → jimmy`
- 对外方案/长文：`jimmy → scout/main → deep/sino → kitt → jimmy`

### 2.3 审核链触发规则

以下默认进入审核链：
- `riskLevel = HIGH`
- `taskType = CONFIG_CHANGE`
- 架构设计 / 路由变更 / 新增 agent / 新增 skill
- 对外正式长文 / 对外承诺 / 关键业务判断
- 跨 3 个以上文件，或有效代码改动 > 200 行

## 3. kitt 审核 SLA

### 3.1 超时与处理

| 项目 | 值 | 说明 |
|------|----|------|
| 单次审核超时上限 | 120 秒 | 覆盖大多数复杂审稿场景 |
| 首次超时处理 | 缩小上下文或降为 Sonnet 重试一次 | 控成本、提成功率 |
| 连续两次超时 + HIGH 风险 | 禁止自动放行，升级厂长 | 高风险未审完不能自动过 |
| 连续两次超时 + MEDIUM 风险 | 可标记"未完整审"后暂挂，等待抽查 | 不直接视作通过 |
| 连续两次超时 + LOW 风险 | 可放行，但日志必须记明原因 | 控制成本与效率 |

### 3.2 抽查比例

| 风险级别 | 审核策略 |
|----------|----------|
| HIGH | 100% 全审 |
| MEDIUM | 30% 抽查，或命中敏感关键词时强审 |
| LOW | 15% 抽查，`hash(taskId) % 100 < 15` |

### 3.3 高风险定义

满足任一项即视为高风险：
1. `task_meta.riskLevel = HIGH`
2. `taskType = CONFIG_CHANGE` 且涉及 `openclaw.json` / provider / 凭据 / routing
3. 对外正式承诺、合同级 SLA、政策性说明
4. `taskType = IMPLEMENTATION` 且：
   - 跨 3 个以上文件，或
   - 改动 > 200 行，或
   - 涉及资金、订单、权限等核心路径

### 3.4 每日配额

| 项目 | 值 | 说明 |
|------|----|------|
| kitt 单日最大审核任务数 | 50 | 控制成本，保留给高价值任务 |

超过配额时：
- HIGH 风险：仍保留 kitt 队列，允许延迟
- MEDIUM / LOW：降级为 guard 或抽查，并记日志 `reason=quota_limit`

### 3.5 审核缓存策略

- 模板化、重复性强的场景：若 7 天内 diff < 5%，可仅审 diff 部分
- 固定 pipeline / 固定模板：可维护"已审模式清单"，每 N 次抽查一次
- **高风险配置变更禁止免审缓存**

## 4. Agent 间上下文传递标准

### 5.1 最小公共 schema

所有 agent 的产出统一使用此 JSON 格式，jimmy 用同一套逻辑解析：

```json
{
  "taskId": "string",
  "fromAgent": "string",
  "toAgent": "string",
  "timestamp": "ISO-8601",
  "status": "ok | error",
  "taskMeta": {
    "taskType": "PLAN | IMPLEMENTATION | CONTENT_CN | ANALYSIS_MULTIMODAL | CONFIG_CHANGE",
    "riskLevel": "LOW | MEDIUM | HIGH",
    "size": "SMALL | MEDIUM | LARGE"
  },
  "summary": "string",
  "details": "markdown string",
  "manifests": [
    {
      "file": "string",
      "operation": "create | replace | patch | delete",
      "language": "ts | py | md | json | ...",
      "description": "string",
      "content": "string"
    }
  ],
  "metrics": {
    "latencyMs": 0,
    "tokensIn": 0,
    "tokensOut": 0
  },
  "error": {
    "category": "RETRIABLE | NON_RETRIABLE | RISK_ESCALATION | NONE",
    "message": "string"
  },
  "nextActions": ["string"]
}
```

### 5.2 使用规则

- 任务含文件生成要求时，必须用此格式返回
- 纯分析类任务可直接输出自然语言，无需 JSON 包装
- `status: "error"` 时 `error.category` 必填，用于 jimmy 判断走重试还是降级
- `manifests` 兼容现有 manifest 机制（`apply_manifest.py`）

## 5. 灰度试运行标准

### 5.1 灰度周期

| 项目 | 值 | 说明 |
|------|----|------|
| 灰度持续时间 | 7–10 天 | 覆盖一个完整工作周 |

### 5.2 关键指标

| 指标 | 达标线 |
|------|--------|
| 任务成功率 | ≥ 90% |
| 严重错误率（P0/P1） | = 0 |
| 平均响应时间变化 | 相比 v2.0 增长 ≤ 20% |
| 人工介入率 | ≤ 10% |
| 配置/规则回滚次数 | ≤ 1 次 |

补充观察指标：
- kitt 拦下的 `🔴 blocker` 数量
- 高风险误放行数量
- 厂长主观满意度

### 5.3 通过 / 失败判定

**通过**：
- 完整跑满 7–10 天
- 成功率 ≥ 90%
- 无 P0/P1 事故
- 平均时延增幅 ≤ 20%
- 人工介入率 ≤ 10%

**失败**：满足任一项即可
- 出现 ≥ 1 次 P0/P1 事故
- 成功率 < 80%
- 平均时延增幅 > 40%
- 人工介入率 > 25%

### 5.4 失败后的处理

1. **单点规则/配置问题**
   - 回滚到上一个稳定版本
   - 写明 root cause
   - 修补后在 sandbox 回归，再小范围重启灰度

2. **架构性问题**
   - 暂停 v2.2，生产整体回退 v2.0
   - 只保留已证明有效的局部改动（如 guard 守门）
   - 重新评审后再设计 v2.3

### 5.5 灰度期间的降级策略

- HIGH 风险任务：即使灰度失败，也不能去掉 `guard + kitt`
- MEDIUM / LOW 风险任务：可临时回退到 v2.0 简化链路（如 `deep → jimmy`）
- 所有 v2.2 新增配置必须绑定回滚版本号，确保 1–2 分钟可回退

### 5.6 适合做灰度的项目

推荐：
- 复杂度中等、覆盖面广
- 同时覆盖 `PLAN / IMPLEMENTATION / CONTENT_CN / CONFIG_CHANGE` 中至少 3 类
- 有明确验收标准
- 对时延中等敏感，不是毫秒级实时场景

不推荐：
- 支付 / 计费 / 核心订单路径
- 样本量太少或任务太碎的项目
