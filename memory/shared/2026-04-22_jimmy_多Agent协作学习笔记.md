## 一、为什么要多 Agent，不用单个大模型？

- 单 Agent 面对复杂任务会撑爆上下文窗口、延迟高、成本失控
- 专业化 Agent 各司其职，更容易调试、更便宜、更快迭代
- 多 Agent 协作在复杂目标上成功率比单 Agent 高 **70%**（arxiv 研究数据）

## 二、四大核心协作模式

### 1. 主管-工人模式（Supervisor-Worker）
最常见。主管 Agent 拆解任务 → 分发给专业 Worker → 汇总结果。

**适用场景**：任务有清晰分解结构（研究+写作、数据采集+分析）

**踩坑点**：主管不能太重，它的职责是**协调**不是**计算**，否则成为瓶颈。

**对应我们的架构**：jimmy 就是主管，kitt/deep/scout/sino 是 Worker。✅ 已在用。

---

### 2. 同行评审模式（Peer Review）
一个 Agent 生产输出 → 另一个 Agent 审查批评 → 原 Agent 修改。

**适用场景**：输出质量要求高的任务（合同、方案、对外报告）

**踩坑点**：必须设定终止条件（如"评分 ≥8 分才通过"），否则无限循环。

**对应我们的架构**：kitt 的"质量门禁/Reality Checker"机制就是这个模式。✅ 已在用。

---

### 3. 并行专家模式（Parallel Specialist）
多个 Agent 同时处理独立子任务 → 汇总 Agent 合并结果。

**适用场景**：研究密集型任务、多数据源采集、子任务互相独立

**性能收益**：并行执行比串行快 **60-80%**

**踩坑点**：各 Agent 返回结构化输出（JSON/评分/要点），不要返回大段散文，否则汇总 Agent 压力极大。

**对应我们的架构**：目前 jimmy 派发子任务基本是串行的，这里有优化空间。⚠️ 可改进。

---

### 4. 辩论模式（Debate Pattern）
多个 Agent 对同一问题持不同立场辩论 → 裁判 Agent 综合最优答案。

**适用场景**：高风险决策、战略选择、需要多角度验证的判断

**原理**：LLM 在"反驳自己"时输出更准确（研究证明）

**对应我们的架构**：目前未使用，适合引入到重大决策场景（如战略规划、方案评审）。🆕 可新增。

## 三、生产级部署的 9 条铁律（精炼版）

### 架构层
1. **两层架构原则**：主 Agent + 专业子 Agent，不要超过两层嵌套。层级越深，调试越难、成本越高。
2. **单一职责**：每个 Agent 只做一件事，职责边界清晰。

### 稳定性层
3. **超时控制**：每个 Agent 调用必须设超时（建议 <30 秒/次），长任务拆成小块串行处理。
4. **降级链**：Agent 失败要有自动降级路径，不能让整个流程卡死。
5. **结构化交接**：Agent 之间传递的数据格式要提前定义好（JSON/Schema），不能靠自然语言随意传。

### 成本层
6. **成本优先选模型**：多 Agent 系统每次用户请求可能触发数千次 LLM 调用，必须用便宜模型做主力，贵模型只用于关键节点。
7. **并行替代串行**：独立子任务并行跑，节省 60-80% 时间。

### 可观测层
8. **监控三层指标**：Agent 级（执行时间/成功率/token 用量）、系统级（端到端耗时/总成本）、业务级（任务完成率）。
9. **人在回路（Human-in-the-loop）**：高风险输出（对外发送、财务操作）在最后一步加人工确认，不全自动。

## 四、真实案例

### 案例 1：销售外联邮件生成（Mindra）
- Research Agent → Persona Agent（并行）→ Signal Analyzer → Copywriter → Reviewer
- 全流程 <90 秒/条，效果比人工写的还好
- 最后一步人工确认再发送

### 案例 2：合规合同审查
- Drafter Agent 生成合同条款 → Reviewer Agent 用合规清单评审
- 只有通过评审的条款才进入下一步
- 法律审查时间减少 60%

### 案例 3：竞品分析（并行专家模式）
- 定价 Agent + 产品功能 Agent + 新闻 Agent + 用户评论 Agent 同时跑
- Synthesis Agent 汇总四路输出生成报告

## 五、对我们（红太阳 Kitt 系统）的启示

| 现状 | 问题 | 改进方向 |
|------|------|----------|
| jimmy 串行派发子任务 | 慢，浪费时间 | 独立子任务改并行派发 |
| 子 Agent 输出格式不统一 | 汇总难，容易出错 | 强制 manifest JSON 格式交接 |
| 无辩论/多视角机制 | 重大决策缺乏验证 | 引入 Debate 模式用于战略决策 |
| 超时控制不完善 | 偶发卡死 | 每个子 Agent 调用加 90s 超时 |
| 监控基本靠日志 | 看不到成本/成功率趋势 | 补充 Agent 级指标记录 |

## 六、一句话总结

> 多 Agent 协作的本质是**团队管理**：清晰的角色分工 + 明确的交接协议 + 轻量的协调层。架构越简单越好，两层够用，并行优于串行，结构化优于自然语言。
