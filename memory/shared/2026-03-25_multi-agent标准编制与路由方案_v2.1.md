# 多-Agent 标准编制与路由方案 v2.1（整合升级版）

> 路径定位：本稿为**审核稿**，用于先审后定稿。
> 建议流程：`shared/方案稿 → Kitt 审核 → 定稿 → 回写权威规则与配置`。
> 目标：不是推翻现有系统，而是**保留三个月磨合出来的有效规则**，并在此基础上补齐岗位、路由、审核链和守门机制。
> 时间：2026-03-25

---

## 一、结论先说

这次方案**不是从无到有发明一套新系统**，而是对现有体系做一次**结构化升级**。

准确说法应该是：

- **旧系统骨架已经成熟**：`jimmy / deep / main / kitt`
- **旧系统方法论已经很强**：Reality Checker、Project Shepherd、先侦察后执行、manifest 落地、模型按特质路由
- **这次新增的价值**：把 `sino / scout / guard` 正式编制化，把 fallback / 风险守门 / 供应链审计单独制度化
- **这次需要修正的地方**：不能因为扩编，就把旧系统已经验证过的“硬规则”冲淡或覆盖掉

所以，v2.1 的目标不是“换系统”，而是：

**旧系统精华保留 + 新岗位补齐 + 路由升级 + 审核链强化**

## 二、现有系统最有价值、必须保留的部分

### 1. 四员骨架已经是成熟雏形

现有体系里最值钱的不是模型名，而是角色分工：

- `jimmy`：调度中枢 + 快速响应 + 看板维护
- `deep`：执行主力（写手 / 码农 / 自动化）
- `main`：纯输入处理器（长文 / 多模态）
- `kitt`：质量门禁 + 深度推理 + 终审裁判

这一骨架是对的，说明系统已经不是“谁都干一切”的混沌状态。

### 2. Reality Checker 是旧系统精华，不能丢

旧系统已经磨出了一个非常成熟的机制：

- 执行和审核分离
- `kitt` 负责终审
- 反馈分层：
  - `🔴 blocker`
  - `🟡 suggestion`
  - `💭 nit`
- 审核要一次性完整反馈，不能滴灌式挑刺

这套机制直接决定系统能不能防幻觉、防自嗨、防“看上去完整、其实经不起推敲”的垃圾交付。

### 3. Project Shepherd 让 `jimmy` 不只是派单员

旧系统里，`jimmy` 不只是路由器，更是任务闭环官，负责：

1. 定义里程碑
2. 标记阻塞项
3. 标记依赖关系
4. 触发升级路径
5. 验收收口

这一点必须保留。否则多-agent 很容易变成“会派活，但不会收口”。

### 4. “先侦察后执行”是高价值纪律

旧系统里有一条非常成熟的核心原则：

**高难度任务不准上来就动手，必须先碰撞，后执行。**

这是系统级省 token、提质量、降返工的纪律，不是形式主义。

适用场景包括：

- 架构设计
- 跨 3 文件以上改造
- 代码超过 200 行
- 没有明确实现路径
- 厂长明确要求“好好想想”

这个原则必须从 v1.1 原样继承，并升级为正式铁律。

### 5. manifest 落地机制非常硬，必须保留

旧系统已经证明：

- 子 agent 不直接乱写盘
- 统一由 `jimmy` 落地
- 统一验收
- 防上下文污染
- 防写文件成功率低

这一套比“让 agent 自己想怎么写就怎么写”稳定得多，必须保留。

### 6. 模型路由逻辑已经成熟

旧系统最成熟的一点之一是：

**路由依据不是模型贵不贵，而是：特质 × 擅长领域 × 当前稳定性。**

这意味着系统不是盲目追求“最强模型”，而是追求：

- 当前谁最适合
- 当前谁最稳定
- 当前谁最划算
- 当前谁能交付

这条要保留，而且应继续作为总路由铁律。

## 三、这次升级真正新增了什么

### 1. 新增 `sino`

定位：中文专家。

适合承接：

- 中文改写
- 润色
- 营销表达
- 销售语境
- 本地化总结

意义：把原来落在 `deep` 身上的中文内容压力拆开，让 `deep` 更聚焦执行与技术产出。

### 2. 新增 `scout`

定位：侦察岗 / Researcher。

适合承接：

- GitHub 对标
- 外链内容侦察
- 竞品、框架、方法论收集
- 公开情报整理

意义：把“找资料”从“执行”里剥离出来，形成真正的**先侦察、后执行**结构。

### 3. 新增 `guard`

定位：守门岗 / Auditor。

适合承接：

- 配置改动前检查
- schema / 漂移 / 回滚核对
- 安全红线审查
- 供应链审计
- skill / MCP / 新依赖风险检查

意义：把过去分散在规则里的安全、回滚、配置一致性要求，固定成一个专门岗位，不再靠“谁想起来谁审”。

### 4. 新增 fallback / 熔断 / reroute 机制表达

旧系统已经有 fallback 思路，但 v2.1 要更明确：

- 单 agent 失败后谁接手
- 连续失败后何时升级 `kitt`
- 高风险任务何时停止自动化并转人工确认
- 哪些错误属于“可重试”，哪些属于“必须熔断”

这部分是制度化补齐，不是推翻旧逻辑。

## 四、v2.1 的正式整合原则

### 原则 1：保留四员骨架，新增三岗，不推翻旧体系

正式编制调整为 7 员：

- `jimmy`
- `deep`
- `main`
- `kitt`
- `sino`
- `scout`
- `guard`

但其中：

- 四员骨架仍是主结构
- 三个新增岗位是补位，不是夺权

### 原则 2：旧系统硬规则优先继承，不因扩编而变软

以下规则必须从旧版直接继承：

1. Reality Checker
2. Project Shepherd
3. 先侦察后执行
4. manifest 统一落地
5. 特质 × 擅长领域 × 当前稳定性 路由
6. 高风险结果必须进入审核链

### 原则 3：新增岗位必须真正解决老问题，而不是只多几个名字

- `sino` 解决中文表达专岗缺失
- `scout` 解决调研与执行混在一起
- `guard` 解决配置与安全审核没人专管

如果新增岗位不解决实际问题，就不应存在。

## 六、v2.1 正式职责边界

### `jimmy`

**核心定位**：调度中枢 + Project Shepherd + 对外统一出口。

**做**：

- 接任务

- 定义里程碑

- 验收收口
- 对外统一回复
- 维护 `task-board.json`
- 统一执行文件写入（子 agent 返回 manifest）

**不做**：

- 不长期写长文
- 不长时间消化大资料
- 不承担终审角色

**核心定位**：首席执行牛马。

**做**：

- 写脚本

- 技术方案初稿
- 长文产出

- 不做终审
- 不单独放行高风险结果
- 不做最终战略拍板

**核心定位**：输入处理器。

- 海量输入消化

## 七、v2.1 路由铁律（整合版）

1. **不该自己干的绝不自己干**
2. **不该问的绝不问**
3. **复杂任务先拆，再派，再收口**
4. **高难度任务必须先侦察后执行**
5. **高风险结果必须进入审核链**
6. **路由依据是特质 × 擅长领域 × 当前稳定性**
7. **稳定性优先于成本**
8. **收到失败结果必须当轮处理，不拖**
9. **子 agent 不直接乱写关键文件**
10. **所有任务最终都要回到 `jimmy` 收口**

## 八、v2.1 的“先侦察后执行”正式化

### 触发条件（满足任一条即触发）

- 架构设计
- 跨 3 文件以上协同修改
- 代码超过 200 行
- 没有明确实现路径
- 厂长明确说“好好想想”
- 外链、竞品、方案型任务需要先对标

### 标准流程

1. **侦察阶段**：优先 `scout` / 必要时 `kitt`
   - 输出：框架、方案、步骤、边界条件、风险点
2. **执行阶段**：`deep` / `main` / `sino`
   - 按图施工，不边想边乱扩
3. **审核阶段**：`guard` / `kitt`
4. **收口阶段**：`jimmy`

### 原则

**先侦察不是拖延，而是为了避免盲干。**

## 九、Reality Checker（v2.1 明确保留）

`kitt` 继续作为唯一正式 `Reality Checker / Verifier`。

### 审核输出格式统一为三层

- `🔴 blocker`：必须修改，不改不能交付
- `🟡 suggestion`：建议修改，不阻断交付
- `💭 nit`：细节优化，可后补

### 审核主轴固定为

1. 正确性
2. 安全性
3. 可维护性
4. 性能 / 成本
5. 测试与验收覆盖
6. 与现有规则 / 记忆 / 配置是否一致

### 必须经过 `kitt` 审的内容

- 架构设计
- 跨 3 文件以上代码改造
- 对外正式长文
- 系统级规则文档
- 高风险自动化方案
- 重大业务判断

## 十、Project Shepherd（v2.1 明确保留）

`jimmy` 必须继续承担 `Project Shepherd` 角色。

### 必做职责

1. 定义里程碑
2. 标记阻塞项
3. 标记依赖关系
4. 触发升级路径
5. 验收收口

### 对厂长汇报统一收敛为三态

- `已完成`
- `卡住`（必须写清卡点）
- `待确认`（仅高风险前）

### 禁止无信息量状态

- `我看下`
- `稍等`
- `我去查`
- `应该可以`

## 十一、manifest 落地机制（v2.1 继续保留）

### 核心原则

- 子 agent 只负责生成结果
- 关键文件由 `jimmy` 统一落地
- 长任务结果不能把全文污染主上下文
- 落地后必须验收

### 好处

- 提高写文件成功率
- 降低上下文污染
- 保证可重试
- 方便审计和回滚

---

## 十二、守门机制（v2.1 新增并制度化）

`guard` 负责把过去分散的安全、配置、供应链规则集中化。

### 强制触发 `guard`

1. `openclaw.json` 变更
2. 路由规则变更
3. 凭据处理
4. 新 skill / MCP / 新依赖接入
5. 回滚方案核对
6. 配置漂移检查

### `guard` 审查主轴

1. 有没有明文密钥
2. 有没有 schema 风险
3. 有没有破坏现有路由
4. 有没有供应链投毒风险
5. 有没有一键回滚方案

## 十三、推荐协作链（正式版）

### 1. 方案型任务

`scout → deep/main → kitt → jimmy`

### 2. 中文内容型任务

`scout（如需材料） → sino → kitt（正式稿） → jimmy`

### 3. 技术实现型任务

`scout（如需先侦察） → deep → guard（若涉配置） → kitt（复杂改造） → jimmy`

### 4. 多模态分析型任务

`main → deep（如需执行） → kitt（关键结论） → jimmy`

### 5. 配置变更型任务

`执行方 → guard → 必要时 kitt → 人工确认 → jimmy`
