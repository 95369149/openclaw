## 1. 设计目标

本方案不是为了“堆更多 agent”，而是为了解决当前体系的 5 个核心问题：

1. **调度与执行混杂**：`jimmy` 既当入口又时常亲自下场，容易把上下文搞脏。
2. **审查角色不够制度化**：`kitt` 虽承担终审，但触发条件、反馈格式、拦截边界没有完全标准化。
3. **外部侦察缺专岗**：GitHub、外链、竞品、框架方法论收集没有稳定角色承接。
4. **配置守门缺专岗**：配置变更、规则漂移、回滚校验缺少单独守门人。
5. **中文内容岗未制度化**：`sino` 已加入编制，但还没进入正式路由和审核链。

因此，本方案目标是建立一套 **7 角架构**：

- `jimmy`：Orchestrator / 总调度
- `deep`：Executor / 执行主力
- `main`：Multimodal Analyst / 多模态输入处理
- `kitt`：Reality Checker / Strategist / 终审
- `sino`：Chinese Specialist / 中文专家
- `scout`：Researcher / 外部侦察
- `guard`：Guard / Auditor / 配置守门

## 2. 对标原则（吸收 GitHub 主流框架共性）

### 2.1 调度、执行、审核三分离

- **调度者** 不应长期深度执行。
- **执行者** 不应自己放行高风险结果。
- **审核者** 不应顺手接管普通生产任务。

### 2.2 专岗优先于全能岗

成熟多-agent框架普遍不是“每个 agent 都能干一切”，而是：

- Researcher 查资料
- Executor 干活
- Reviewer 挑错
- Specialist 做专门领域
- Guard 盯风险

### 2.3 多-agent 仅用于“可拆分任务”

适合多-agent：

- 调研 → 分析 → 产出 → 审核
- 多来源并行收集
- 方案比较与交叉审查

不适合多-agent：

- 极短小、单轮可完成的问题
- 强耦合、强连续性的配置手术
- 单点明确任务，拆了反而增加误差

### 2.4 权限边界必须显式

边界不仅体现在模型能力，也体现在：

- 谁能派发
- 谁能执行
- 谁只能给证据
- 谁只能审计
- 谁必须人工确认后才可推进

### 2.5 重要结果必须进入审核链

以下类别默认进入审核链：

- 架构设计
- 配置变更
- 高风险脚本
- 对外发布内容
- 关键业务判断

## 3. 7 角标准编制

### 3.1 `jimmy`

- 角色：总调度 / 对外统一出口 / 项目 shepherd
- 主模型：`mynewapi/claude-sonnet-4-6`
- 核心职责：
  - 接收厂长需求
  - 判断是否自己直接完成
  - 选择目标 agent
  - 汇总多 agent 结果
  - 向厂长输出最终结论
  - 维护任务状态与交付闭环
- 不负责：
  - 大规模资料消化
  - 超长内容生产
  - 复杂终审裁决
- 原则：**保持主上下文干净，能调度就不硬扛。**

### 3.2 `deep`

- 角色：执行主力 / Builder / 自动化与代码实现
- 主模型：`mygptapi/gpt-5.4`
- 核心职责：
  - 代码、脚本、自动化
  - 批处理
  - 技术文档初稿
  - 数据整理与结构化交付
  - 面向结果的执行工作
- 不负责：
  - 终审
  - 风险放行
  - 最终战略拍板
- 原则：**以落地为先，但不自己给高风险结果盖章。**

### 3.3 `main`

- 角色：多模态输入处理 / 长文档分析
- 主模型：`google-gemini-cli/gemini-3-pro-preview`
- 核心职责：
  - 图片 / 视频 / PDF / 长网页理解
  - 大体量文本归纳
  - 多模态证据读取
  - 长上下文摘要
- 不负责：
  - 配置变更拍板
  - 复杂系统审计
  - 最终业务判断
- 原则：**负责看懂，不负责拍板。**

### 3.4 `kitt`

- 角色：Reality Checker / 终审 / 战略判断 / 架构裁判
- 主模型：`mynewapi/claude-opus-4-6`
- 核心职责：
  - 审核架构、复杂代码、关键方案
  - 识别漏洞、不一致、风险、逻辑硬伤
  - 对重大决策做最终质量门禁
  - 对厂长给出高价值判断意见
- 不负责：
  - 普通流水生产
  - 低价值批处理
- 原则：**只审结果，不替执行岗打杂。**

### 3.5 `sino`

- 角色：中文专家 / 本地化表达 / 中文内容岗
- 主模型：`kimi/kimi-for-coding`
- 核心职责：
  - 中文改写、润色、总结
  - 中文营销文案
  - 中文客服/销售场景表达
  - 本地化措辞与语气优化
- 不负责：
  - 架构决策
  - 高风险配置
  - 系统级审核
- 原则：**负责把中文说得准、顺、像人。**

### 3.6 `scout`

- 角色：Researcher / GitHub 与外部情报侦察
- 主模型：`google-gemini-cli/gemini-3-pro-preview`
- 核心职责：
  - GitHub 方案对标
  - 外链与公开资料侦察
  - 竞品、框架、方法论收集
  - 事实证据整理
- 不负责：
  - 最终结论拍板
  - 高风险执行
  - 配置修改
- 原则：**只查事实、交证据，不直接定方向。**

### 3.7 `guard`

- 角色：Guard / Auditor / 配置守门人
- 主模型：`mynewapi/claude-sonnet-4-6`
- 核心职责：
  - 配置变更前检查
  - schema / 漂移 / 回滚校验
  - 审查安全红线
  - 审核规则文档与配置是否一致
  - 对供应链风险、安装链、明文密钥等问题做拦截
- 不负责：
  - 普通问答
  - 内容生产主力
  - 最终业务判断
- 原则：**只守门，不抢活。**

## 5. 路由规则

### 5.1 总入口

- 所有需求先进入 `jimmy`。
- `jimmy` 负责做 3 秒内路由判断：
  1. 自己直做
  2. 单 agent 派发
  3. 多 agent 协作
  4. 高风险待确认

### 5.2 单 agent 直派规则

| 任务类型                                 | 默认 agent |
| ---------------------------------------- | ---------- |
| 简单问答、轻量状态查询、轻量文件读写     | `jimmy`    |
| 代码、脚本、自动化、数据处理             | `deep`     |
| 图片、视频、PDF、长文档、网页视觉理解    | `main`     |
| 中文文案、改写、润色、总结、本地化表达   | `sino`     |
| GitHub、竞品、外链、情报收集             | `scout`    |
| 架构、战略、关键审查、复杂判断           | `kitt`     |
| 配置审计、风险检查、回滚核对、规则一致性 | `guard`    |

### 5.3 多 agent 协作规则

适用于以下场景：

1. **调研 + 决策**：`scout` 先查，`kitt` 终审。
2. **多模态 + 执行**：`main` 先理解输入，`deep` 负责产出。
3. **内容 + 审核**：`sino` 先写中文稿，`kitt` 审核对外版本。
4. **技术 + 审核**：`deep` 先实现，`kitt` 审代码/架构。
5. **配置 + 守门**：执行前 `guard` 必查，必要时再由 `kitt` 做高阶审查。

### 5.4 禁止滥用多跳

- `scout` 不应继续向下派发，只交事实。
- `guard` 不应继续向下派发，只给审计结论。
- `sino` 不应继续向下派发，只做中文表达。
- `deep` 默认不派发，除非后续制度特别放开。
- `jimmy` 和 `kitt` 是主要路由节点。

## 6. 协作闭环

### 6.1 标准闭环

1. `jimmy` 接任务
2. 选路由
3. 目标 agent 执行
4. 结果写入共享产物 / 返回摘要
5. 必要时进入 `kitt` / `guard` 审核
6. `jimmy` 汇总给厂长
7. 重要信息落盘到记忆

### 6.2 审核链

- **技术审核**：`deep` → `kitt`
- **方案审核**：`scout` / `deep` / `main` → `kitt`
- **内容审核**：`sino` → `kitt`（仅对外正式稿强制）
- **配置审核**：执行方 → `guard` → 必要时 `kitt` → 人工确认

### 6.3 汇报责任

- 对厂长的最终口径统一由 `jimmy` 输出。
- `scout` / `deep` / `main` / `sino` / `guard` 的结果默认不直接面向厂长裸奔。
- 除非厂长明确要求，否则中间产物不直接打扰厂长。

## 7. 权限边界

### 7.1 调度岗：`jimmy`

- 可以调度、汇总、轻执行
- 不应长期背重任务

### 7.2 执行岗：`deep`

- 可以做代码、脚本、批处理
- 不得自审放行高风险结果

### 7.3 输入岗：`main`

- 可以读取多模态和大体量输入
- 不负责系统级拍板

### 7.4 审核岗：`kitt`

- 可以否决结果、提出 blocker
- 不应沦为普通生产牛马

### 7.5 中文岗：`sino`

- 可以承担中文表达优化
- 不得越权进入高风险配置和审计

### 7.6 侦察岗：`scout`

- 只给证据、不拍板
- 不做配置写入

### 7.7 守门岗：`guard`

- 只做审计与拦截
- 不接普通生产任务

## 8. 强制触发规则

以下情况必须经过 `kitt`：

1. 架构设计
2. 复杂代码改造
3. 对外正式长文
4. 高风险业务判断
5. 涉及 3 步以上复杂推理的关键决策

以下情况必须经过 `guard`：

1. `openclaw.json` 变更
2. 路由规则变更
3. 密钥/凭据处理
4. 新 skill / 新 MCP / 新依赖安装前审计
5. 回滚方案核对

---

## 9. 供应链与安全规则（并入 `guard`）

参考近期 `litellm` 供应链事件，本方案明确加入以下制度：

1. **新 Skill / MCP / 第三方工具安装前必须审计**。
2. **自动 `pip install` / `npm install` / 安装脚本视为高风险动作**。
3. 审计范围包括：
   - 是否读取环境变量
   - 是否写入 `~/.openclaw/`
   - 是否包含 `curl | sh` / base64 混淆 / 外发请求
   - 是否会收集 SSH / 云凭据 / token / shell history
4. 明文密钥不得写入配置文件，必须使用环境变量引用。
5. 配置变更必须带回滚方案。

## 10. 建议的派发权限结构

这是后续写入 `openclaw.json` 的建议目标：

- `jimmy` 可派：`main`, `deep`, `kitt`, `sino`, `scout`, `guard`
- `kitt` 可派：`deep`, `main`, `sino`, `scout`, `guard`
- `main` 可派：`deep`, `kitt`, `sino`
- `deep` 可派：`[]`
- `sino` 可派：`[]`
- `scout` 可派：`[]`
- `guard` 可派：`[]`

设计意图：

- 让 `jimmy` 成为主路由中枢
- 让 `kitt` 在高阶审查时拥有最小但足够的二次调度权
- 让 `main` 在多模态输入转执行/转中文整理时有轻量协作能力
- 避免全员互相派发，防止系统失控

## 11. 与现有体系的关系

本方案不是推翻旧体系，而是把现有结构升级为标准化编制：

- 保留已有核心角色：`jimmy`, `deep`, `main`, `kitt`
- 正式纳入新增角色：`sino`, `scout`, `guard`
- 把原先隐含的经验规则，升级成可审核、可落地、可同步到配置的明确制度

## 14. 一句话结论

最终目标不是“更多 agent”，而是：

**7 角分工 + 固定路由 + 独立审核 + 守门机制 + 供应链审计前置**。

只有这样，这套多-agent系统才算从“能跑”升级到“有制度地稳定交付”。
