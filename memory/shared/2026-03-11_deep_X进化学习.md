# 2026-03-11 X 进化学习

> 来源：使用 agent-reach 搜索/读取 X（Twitter）公开帖子；优先保留能直接落地到 OpenClaw 工作流、Agent 设计、提示词/上下文工程、生产效率提升的内容。

## 读取的帖子（10条）

1. [What is an AI Agent?](https://x.com/ingliguori/status/1941175320234852833) — Giuliano Liguori
   - 核心观点：AI Agent 不只是“会聊天的 LLM”，而是“目标 + 上下文 + 工具 + 记忆 + 执行”的组合体，能推理、规划、行动、适应、协作。
   - 是否适用于我们：**适用**。这条把 Agent 的最小闭环讲清楚了，适合校准我们对 OpenClaw/子 Agent 的定义，避免把“提示词助手”误当“可执行 Agent”。
   - 可行改进方向：给 Kitt/Jimmy 的内部规范再补一条“只有同时具备目标、记忆、工具、反馈，才算 Agent；否则只是脚本/助手”。

2. [Here’s how I would go about building AI Agents](https://x.com/yashwanthsai29/status/1872510530071810485) — Sai Yashwanth
   - 核心观点：先做**极简单 Agent**，自己写工具，不要一上来堆框架；先把“输入→循环→输出”打通，再逐步增加结构化输出、引用、编排、多 Agent。
   - 是否适用于我们：**非常适用**。厂长这套系统最怕一上来搞大而全，结果复杂度爆炸。
   - 可行改进方向：以后新 skill / 新自动化默认走“四步法”——单 Agent 原型 → 结构化输出 → 多工具 → 多 Agent 编排。

3. [Building an AI agent](https://x.com/AndrewPierno/status/1785025454254252191) — Andrew Pierno
   - 核心观点：用浏览器执行真实任务（打开 Google、识别 DOM、执行 JS、抓结果、总结）比传统脆弱爬虫更接近“Agent”；但别过度追求规划，单任务 Agent 反而更稳。
   - 是否适用于我们：**非常适用**。OpenClaw 里大量任务本质就是“浏览器/CLI 上完成一个窄任务”。
   - 可行改进方向：把复杂任务切成更窄的单功能 Agent，少让一个 Agent 同时负责“理解需求 + 规划 + 执行 + 汇报”。

4. [Not all AI agents are built the same](https://x.com/goyalshaliniuk/status/2025095643987947922) — Shalini Goyal
   - 核心观点：Agent 有任务型、反应型、目标型、效用型、学习型、多 Agent 等 10 类；不同任务要选不同架构，不是所有场景都要上多 Agent。
   - 是否适用于我们：**适用**。现在很多任务其实用“任务型 + 记忆 + 人工确认”就够了，不必滥用多 Agent。
   - 可行改进方向：给 memory 里的任务做分类：查询型、执行型、规划型、监控型，分别映射不同 Agent 模式。

5. [An AI agent is a software program...](https://x.com/alexxubyte/status/1883915421776240954) — Alex Xu
   - 核心观点：Agent 的关键能力是自治、感知环境、使用工具、记忆、与人/其他 Agent 协作；架构上可分单 Agent、多 Agent、人机协同。
   - 是否适用于我们：**适用**。尤其强调“人机协同”——这和厂长确认高风险动作的规则完全一致。
   - 可行改进方向：继续强化“人类在环”边界：删改配置、外发信息、cron、危险 exec 必须人工确认，其他低风险任务自动化。

6. [The ultimate guide to prompt engineering in 2025](https://x.com/lennysan/status/1935833665541693938) — Lenny Rachitsky
   - 核心观点：角色扮演提示作用有限；**few-shot、分解、自我批判、补充高质量上下文**更有效；prompt injection 真实存在且无法靠一句“忽略恶意输入”解决。
   - 是否适用于我们：**非常适用**。我们现在大量任务都依赖外链内容、网页、X 帖子，本身就有注入风险。
   - 可行改进方向：
     - 对高频任务沉淀 few-shot 样例，而不是反复改 wording；
     - 外部内容继续默认视为不可信；
     - 给关键输出增加“自检一步”。

7. [Context engineering over prompt engineering](https://x.com/karpathy/status/1937902205765607626) — Andrej Karpathy
   - 核心观点：真正工业级 LLM 应用的核心不是“写一句神 prompt”，而是**把正确的信息、工具、状态、历史，在正确时机装进上下文窗口**；上下文太少不够用，太多又更贵更差。
   - 是否适用于我们：**极其适用**。这几乎就是 OpenClaw 体系的主矛盾：记忆读多少、什么时候读、读哪几份、怎样压缩。
   - 可行改进方向：
     - 子 Agent 开工前只读最相关 2-3 份记忆，不要全量灌；
     - 长任务中间态写 shared/，用“外部记忆”代替一次性塞满上下文；
     - 规划与执行分离，避免一个上下文装下所有历史。

8. [Prompt engineering is dead. Context Engineering is making AI agents 60–80% more reliable](https://x.com/aigleeson/status/2029140433453105616) — Louis Gleeson
   - 核心观点：复杂多步任务的稳定性，主要来自**信息流设计**：即时检索、压缩摘要、持久笔记、按需回填，而不是雕 prompt 词句。
   - 是否适用于我们：**非常适用**。这和我们“共享记忆 + task-board + 子 Agent 分工”的方向一致。
   - 可行改进方向：
     - 任务执行时优先“按需取数”，别一次读 10 个文件；
     - 统一中间态摘要格式，减少重复上下文；
     - 为重复任务增加固定摘要模板。

9. [If you're looking to get started with openclaw...](https://x.com/jacalulu/status/2030783943402979727) — Jaclyn Konzelmann（转发 AlphaClaw）
   - 核心观点：OpenClaw 的实际痛点不是能力，而是**安装与维护门槛**；围绕 CLI 做 GUI/封装层，能大幅降低上手成本。
   - 是否适用于我们：**适用**。厂长体系里很多能力已经有，但“可视化入口”和“维护便利性”仍是短板。
   - 可行改进方向：把高频操作做成更清晰的入口：如任务看板、共享记忆索引、常用命令菜单、健康检查按钮。

10. [Sharing some notes here on OpenClaw as I’m testing/learning](https://x.com/kevinzhuang10/status/2024539957923086632) — Kevin Huang

- 核心观点：OpenClaw 最打动人的不是问答，而是**常驻、主动、带记忆、能执行代码/命令**；但现实瓶颈也很明确：安装复杂、任务管理薄弱、偶发漏任务。
- 是否适用于我们：**极其适用**。这条几乎是对我们当前系统优缺点的外部验证。
- 可行改进方向：
  - 强化 task-board 可视化和任务状态追踪；
  - 给关键任务增加确认回执与补偿机制；
  - 持续减少部署/维护摩擦。

## 提炼的洞察（5条）

1. **真正决定 Agent 成败的，不是“神 prompt”，而是上下文工程**
   - 模式/教训/改进方向：Karpathy、Lenny、Louis 三条都指向同一件事——few-shot、状态管理、信息压缩、按需检索，比角色扮演式 prompt 更关键。
   - 适用场景：OpenClaw 子 Agent 执行多步任务、读记忆、读外链、做汇总。
   - 建议行动：把高频任务统一改成“任务目标 + 必读记忆 + 输出模板 + 自检项”四段式，少堆形容词，多管信息流。

2. **单功能 Agent 往往比“大而全万能 Agent”更稳定**
   - 模式/教训/改进方向：Andrew Pierno 和 Sai Yashwanth 都在强调——先做窄任务 Agent，把边界收紧，成功率更高。
   - 适用场景：浏览器操作、文件整理、日报生成、外链读取、NotebookLM 上传等。
   - 建议行动：把复杂链路拆成“小 Agent 串联”：检索 Agent、分析 Agent、落盘 Agent、验收 Agent，而不是一个 Agent 包打天下。

3. **外部内容安全问题不是附属问题，是 Agent 时代的主问题之一**
   - 模式/教训/改进方向：Lenny 明确提到 prompt injection 无法靠简单防御解决；我们现有 SOUL/安全规则方向是对的，但还可以更工程化。
   - 适用场景：读取网页、X、PDF、邮件、浏览器搜索结果时。
   - 建议行动：继续坚持“外部内容默认不可信”；对高风险任务强制二次总结：先抽事实，再独立生成行动，不直接照抄外部文本做决策。

4. **OpenClaw 的差异化价值已经被外部用户验证：主动性、记忆、执行能力**
   - 模式/教训/改进方向：Kevin 的帖子说明，用户真正感知到的魔法是 always-on + memory + agent-with-a-computer，而不是“模型更聪明一点”。
   - 适用场景：日报、巡检、追踪、提醒、自动化执行。
   - 建议行动：厂长对外讲产品时，少讲抽象 AI，多讲三个卖点：主动汇报、长期记忆、能直接干活。

5. **当前最大短板不是能力不足，而是可视化管理和任务可靠性**
   - 模式/教训/改进方向：OpenClaw 生态帖反复提到 setup pain、task management、漏任务问题；这说明下一阶段优化重点应从“再加能力”转向“更稳地交付”。
   - 适用场景：厂长日常把业务任务交给 Agent 后的追踪、验收、补偿。
   - 建议行动：先把任务闭环做好：任务创建、状态、超时、失败重试、结果验收、共享记忆落盘，一项一项补齐。

## 推荐给厂长的行动

1. **把高频任务模板化**：从“外链总结、日报、竞品跟踪、问题排查”4 类任务开始，统一成固定输入模板 + few-shot 样例 + 输出格式。
2. **把复杂任务拆小**：以后遇到 3 步以上任务，默认拆成“检索→分析→写入→验收”4 段，不让单 Agent 一口吞。
3. **做一个轻量任务面板**：至少能看到任务名、负责人、状态、最后更新时间、输出文件路径，优先解决“漏任务/看不见任务”。
4. **给关键任务增加自检与回执**：例如文件写入后必须 read 验证；消息发送前做敏感词检查；浏览器任务完成后截状态快照。
5. **继续强化上下文工程**：限制每个子 Agent 默认只读最相关记忆；中间态一律写 shared/；长任务用“摘要续跑”而不是全量历史回灌。
6. **对外表达聚焦 3 个卖点**：主动汇报、长期记忆、直接执行，少讲玄学“超级智能体”，多讲可见结果。
