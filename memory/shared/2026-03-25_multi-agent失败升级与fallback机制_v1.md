# 多-Agent 失败升级 / Fallback / 熔断机制 v1

- 日期：2026-03-25
- 状态：待并入权威规则
- 适用范围：OpenClaw 当前 7-agent 编制（`jimmy`, `deep`, `main`, `kitt`, `sino`, `scout`, `guard`）
- 目标：参考主流多-agent系统在 **retry / fallback / reroute / escalation / validation / circuit breaker** 上的做法，补齐失败处理机制，避免 agent 卡死、静默失败、无限重试、绕过审核链。

---

## 1. 核心原则

### 1.1 失败不能静默

任何 agent 一旦出现以下情况，不得“装作还在运行”：

- 超时
- 空结果
- 输出不可解析
- 上游 4xx/5xx
- 工具连续失败
- 结果不符合预期 schema / 结构

### 1.2 失败先分类，再处理

失败必须先区分类型，再决定重试、改派、升级还是熔断。

### 1.3 有界重试，不准死循环

所有自动重试必须有上限，不准无限 retry。

### 1.4 守门岗失败不能绕过

- `guard` 失败，不能自动放行。
- `kitt` 审核失败，不能自动继续交付。

### 1.5 输出校验失败 = 执行失败

不是“勉强收下”，而是视为失败并进入重试或升级链。

---

## 2. 失败分类

### F1 模型 / Provider 失败

典型表现：

- 401 / 402 / 403
- 429
- 500 / 502 / 503 / 504
- provider 超时
- 协议不兼容

### F2 Agent 执行失败

典型表现：

- 子 agent 超时
- 无结果返回
- 返回内容损坏
- 任务中断
- transcript repair / session history 异常导致输出不可用

### F3 工具链失败

典型表现：

- browser 失败
- web_fetch 被拦截
- exec 失败
- 文件写入失败
- 依赖工具不可用

### F4 路由失配

典型表现：

- 任务派错 agent
- agent 不具备该任务能力
- 执行方向明显跑偏

### F5 输出校验失败

典型表现：

- schema 不符合
- action 格式不符合
- 内容缺关键字段
- 结果与任务目标不一致

---

## 3. 标准处理流程

### Step 1：检测失败

一旦命中 F1-F5 任一类，立即标记“当前执行失败”。

### Step 2：归因

归因为以下四类之一：

- 模型 / Provider 问题
- 工具问题
- 路由问题
- 输出问题

### Step 3：执行有界重试

- **瞬时错误**（429 / 5xx / timeout / 临时网络失败）→ 允许自动重试 1 次
- **明显非瞬时错误**（401 / 403 / 协议不兼容 / schema 错误）→ 不应原地重试，直接改派或升级

### Step 4：fallback / reroute

如果重试后仍失败，进入备用链：

- 换备用 agent
- 换备用模型
- 交由 `jimmy` 或 `kitt` 接管判断

### Step 5：升级 / 汇报

- 普通执行岗：第二次失败后汇报 `jimmy`
- 守门岗 / 审核岗：第一次失败即可触发升级
- 全链路失败：汇报厂长

### Step 6：熔断

满足以下任一条件，进入熔断：

- 同一任务连续 3 次失败
- 同一 provider 在短时间内连续失败
- 同一 agent 多次返回坏格式
- 守门岗失效且无替代校验路径

熔断后动作：

- 停止继续自动重试
- 标记当前链路不可用
- 汇报 `jimmy`
- 必要时汇报厂长

## 4. 分角色失败链

### 4.1 `sino` 失败链

适用：中文改写、中文润色、中文营销文案

处理：

1. `sino` 失败 → 重试 1 次（仅瞬时错误）
2. 仍失败 → 改派 `deep`
3. 若仍需高质量中文判断 → 升级 `kitt`
4. 仍失败 → `jimmy` 汇报厂长

### 4.2 `deep` 失败链

适用：代码、脚本、自动化、批处理

处理：

1. `deep` 失败 → 重试 1 次（仅瞬时错误）
2. 若任务本质偏输入理解 → 改派 `main`
3. 若任务本质偏复杂判断 / 架构 → 升级 `kitt`
4. 若都不适配 → `jimmy` 汇报厂长

### 4.3 `main` 失败链

适用：长文档、多模态输入、PDF/视频理解

处理：

1. `main` 失败 → 重试 1 次（仅瞬时错误）
2. 若任务可降级为纯文本执行 → 改派 `deep`
3. 若结论需要高阶判断 → 升级 `kitt`
4. 仍失败 → `jimmy` 汇报厂长

### 4.4 `scout` 失败链

适用：GitHub 调研、外链侦察、竞品搜集

处理：

1. `scout` 失败 → 重试 1 次（仅瞬时错误）
2. 改由 `jimmy` 自己执行轻量碰撞
3. 如需长文资料吞吐 → 改派 `main`
4. 如需在信息不完整下做判断 → 升级 `kitt`

### 4.5 `guard` 失败链

适用：配置审计、回滚核对、安全检查、供应链审计

处理：

1. `guard` 失败 → **不允许绕过**
2. 立即升级 `kitt`
3. `kitt` 若仍不能完成审计 → 停止自动放行
4. `jimmy` 汇报厂长，等待人工确认

### 4.6 `kitt` 失败链

适用：终审、架构判断、关键决策

处理：

1. `kitt` 失败 → 可重试 1 次（仅瞬时错误）
2. 若仍失败 → 不自动放行
3. `jimmy` 汇报厂长
4. 允许降级给出“未审通过 / 无法完成终审”的状态，但不允许伪装为已完成

---

## 5. 汇报分级

### L1 轻失败

处理方式：系统内部消化，不必打扰厂长

- 瞬时 timeout
- 临时 502 / 503
- 单工具一次性失败

### L2 中失败

处理方式：内部改派，并在状态里留痕

- 当前 agent 不可用
- 已切备用 agent / 模型
- 需要 supervisor 接管

### L3 重失败

处理方式：必须汇报厂长

- `guard` 失败
- `kitt` 失败
- 连续 2 次改派仍失败
- 所有备用链都失败
- 涉及高风险任务无法安全放行

---

## 6. 输出校验门

### 6.1 校验失败视为执行失败

以下情况直接进入失败链：

- 返回内容缺必要结构
- manifest 无法落地
- 工具调用结果不完整
- 结果与任务目标错位

### 6.2 校验优先级

1. 结构正确性
2. 任务完成度
3. 安全性
4. 与权威规则一致性

---

## 7. 熔断规则

### 7.1 Provider 熔断

同一 provider 连续短时间失败达到阈值时：

- 暂时移出默认路由
- 记录状态
- 改走备用链

### 7.2 Agent 熔断

某 agent 连续多次出现：

- 坏格式
- 超时
- 明显跑偏
  则本轮任务中暂停继续使用该 agent。

### 7.3 审核链熔断

如果 `guard` / `kitt` 双双不可用：

- 高风险任务停止自动推进
- 必须人工确认

## 9. 一句话结论

**单 agent 模型失效不应等于卡死。**
正确机制应该是：

**失败分类 → 有界重试 → fallback / reroute → 审核岗不可绕过 → 必要时熔断与人工接管。**
